## 💬 딥다이브 이슈

딥다이브는 하나의 문제나 질문을 **좁고 깊게 탐구**하기 위해 사용한다.

> **이슈 제목 예시**  
> DB 인덱스는 왜 조회 성능을 높일까?

고정된 이슈 템플릿은 사용하지 않는다. 모든 주제에 같은 형식을 적용하면 문제를 탐구하는 것보다 빈 항목을 채우는 데 집중할 수 있기 때문이다.

글의 형식은 자유롭게 선택하되, 다음 학습 원칙은 유지한다.

### 이슈 작성 원칙

| 순서 | 원칙 | 핵심 기준 |
| --- | --- | --- |
| 1 | **Problem-Driven** | 왜 학습하는가? |
| 2 | **Narrow & Deep** | 이번 이슈에서 어디까지 다루는가? |
| 3 | **i+1** | 현재 이해에서 다음 한 단계는 무엇인가? |
| 4 | **Structural Thinking** | 개념이 어떤 흐름과 관계로 동작하는가? |

#### 1. Problem-Driven

> 키워드가 아니라 **해결하려는 문제**에서 시작한다.

개념의 정의를 먼저 나열하지 않는다.  
“왜 이 내용을 학습하는가?”를 정하고 문제 해결에 필요한 내용을 탐구한다.

```text
조회 성능이 느리다.
→ Full Scan과 인덱스를 학습한다.
→ 인덱스가 검색 범위를 줄이는 원리를 이해한다.
```

#### 2. Narrow & Deep

> 하나의 이슈에서는 **하나의 핵심 질문**만 다룬다.

연관된 개념을 넓게 나열하지 않는다. 선택한 문제의 동작 원리와 구조를 설명할 수 있는 수준까지 깊게 학습한다.

현재 질문을 해결하는 데 필요하지 않은 내용은 **비범위**로 판단하고 별도의 이슈로 분리한다.

#### 3. i+1

> 현재 알고 있는 내용보다 **한 단계 깊은 내용**을 학습한다.

한 번에 모든 내용을 이해하려 하지 않는다. 현재 이해한 내용에서 다음 단계 하나만 선택한다.

```text
Full Scan을 알고 있다.
→ B+Tree가 검색 범위를 줄이는 과정까지 학습한다.
```

새로운 질문이 현재 범위를 벗어난다면 기존 이슈를 계속 확장하지 않는다.

#### 4. Structural Thinking

> 개념을 단편적으로 암기하지 않고 **흐름과 관계**로 이해한다.

입력부터 결과까지의 처리 과정과 각 구성 요소의 역할을 연결한다.

```text
SQL 실행
→ 인덱스 탐색
→ 대상 행의 위치 확인
→ 데이터 조회
```

장점과 단점도 따로 암기하지 않는다. 개념의 동작 원리와 구조를 바탕으로 직접 도출한다.

> **목표:** 많은 내용을 기록하는 것이 아니라, 하나의 문제를 자신의 언어로 설명하고 활용할 수 있는 상태에 도달한다.
