# 네트워크 IO와 자원 효율

---

## 1. 서버는 곧 네트워크 프로그램이다

서버 프로그램은 기본적으로 네트워크 프로그램이다. 

서버는 거의 모든 구성 요소와 네트워크를 통해 데이터를 주고받는다.

```
클라이언트 ──HTTP──▶ 서버 ──TCP 기반 프로토콜──▶ DB
                     │  └──────────────────▶ 레디스
                     └──────────────────────▶ 외부 API
```

| 대상 | 통신 방식 |
| --- | --- |
| 클라이언트 | 주로 HTTP 프로토콜 |
| DB | TCP 기반 프로토콜 |
| 레디스(메모리 캐시) | 네트워크 통신 |
| 외부 API | 네트워크 통신 |

API를 만들 때 개발자가 직접 네트워크 프로그램을 작성하지는 않지만, **서버는 네트워크 통신을 기반으로 동작한다는 점이 전제**된다.

## 2. 네트워크 입출력은 결국 `write` / `read`

**네트워크로 데이터를 주고받는 과정**은 두 줄로 정리된다.

```java
outputStream.write(...); // 출력 스트림으로 데이터 보내기
inputStream.read(...);   // 입력 스트림으로 데이터 받기
```

**예: SELECT 쿼리 실행**

1. 서버가 DB와 연결된 **출력 스트림**으로 SELECT 쿼리를 전송한다.
2. DB가 보내는 결과를 **입력 스트림**으로 받는다.

## 3. 블로킹 IO :  스레드는 대기한다

데이터를 보내고 받는 동안, 코드를 실행하던 스레드는 전송이 완료될 때까지 대기한다.

```
스레드
  │  코드 실행
  ├─ write() 시작
  │  ▒ 스레드 대기 (데이터 전송)
  ├─ write() 리턴
  ├─ read() 시작
  │  ▒ 스레드 대기 (데이터 수신)
  ├─ read() 리턴
  │  코드 실행
  ▼
```

!image.png

> **블로킹(blocking)**
작업이 완료될 때까지 **스레드가 대기하는 것.**
> 
> 
> 주로 데이터 입출력 과정에서 발생하며, 그래서 이런 방식을 **블로킹 IO**라고 부른다.
> 

핵심은 **입출력에 걸리는 시간이 코드 실행 시간보다 훨씬 길다**는 것이다. 

네트워크 연동이 많은 서버는 전체 실행 시간의 90% 이상을 입출력 대기에 쓰는 경우도 있다.

**저자의 실측 사례**

- 전체 실행 시간 `800ms` → CPU 사용 시간은 4ms (`99.5%`가 쿼리 실행·외부 API 호출 같은 `IO 처리`)
- 3초 가까이 실행되는데 CPU 사용 시간은 고작 5ms였던 경우도 있음

## 4. 스레드를 늘리면? : 요청당 스레드 방식의 한계

**스레드가 대기한다는 건** 그 스레드를 실행하던 **CPU도 놀고 있다**는 뜻이다. 

CPU 사용률을 높이는 가장 직관적인 방법은 실행할 스레드를 많이 만드는 것 — **요청당 스레드(thread per request)** 방식이 여기에 해당한다(톰캣 등). 

동시 실행 스레드 수를 늘려 IO 대기로 인한 CPU 낭비를 줄일 수 있다.

하지만 두 가지 한계가 있다.

### 1) 메모리

**스레드 하나가 수백 KB ~ 수 MB의 메모리를 사용**한다. 

⇒ 따라서, 스레드 수를 늘리면 스레드가 차지하는 메모리도 늘어나 메모리 병목이 일어난다

> 커넥션당 스레드 방식의 웹소켓 서버에 1만 명이 동시 접속
> 
> 
> → 스레드 1만 개 생성만으로 메모리 사용량이 **10GB에 육박**한다. 사용자가 늘면 메모리가 병목이 된다.
> 
> ⇒ 그렇다면 메모리도 늘리면 되는거 아닌가? (그래도 문제가 발생한다: 컨텍스트 스위칭) 
> 

### 2) 컨텍스트 스위칭

> **컨텍스트 스위칭(context switching)**
운영체제는 여러 스레드를 번갈아 CPU에 할당한다.
> 
> 
> 스레드를 전환하려면 **현재 실행 중인 스레드의 상태를 기록하고, 다음 스레드의 상태 정보를 불러와야** 한다. 이 과정이 **컨텍스트 스위칭**이다.
> 

컨텍스트 스위칭은 마이크로초 단위로 끝나지만, 그동안 CPU는 실질적인 작업을 하지 않는다. 

동시 실행되는 프로세스·스레드가 많아지면 여기에 쓰이는 시간도 무시하기 힘들 만큼 커진다.

### 정리: 트래픽이 증가하면 자원 효율이 떨어지는 2가지 이유

- IO 대기와 컨텍스트 스위칭에 따른 **CPU 낭비**
- 요청마다 스레드를 할당함으로써 **메모리 사용량이 높음**

## 5. 그런데 왜 여전히 톰캣을 쓰는가

서버는 DB·API 호출 같은 입출력 처리가 많고, 이는 요청당 스레드 방식이 CPU와 메모리를 낭비한다는 뜻이다. 그럼에도 대다수 서비스는 자원 낭비를 걱정할 필요가 없다. **CPU와 메모리 사용에 영향을 줄 만큼의 트래픽이 발생하지 않기 때문**이다.

수백만~수천만 이상의 고객이 쓸 정도로 인기 있는 서비스가 아니라면, 자원 부족보다 **다른 이유로** 성능 문제가 생길 때가 많다.

## 6. 처리량을 높이는 두 갈래

서비스가 인기를 끌어 트래픽이 늘기 시작하면, 그때부터 처리량을 높일 방법을 고민하면 된다.

### 방법 1. 자원을 더 확보한다 (수평 확장 / 수직 확장)

- 장점: 기존 프로그램을 수정하지 않아도 되므로 비교적 쉽게 달성
- 단점: **비용과 직결**된다. 클라우드에서 가상 서버를 2개 → 4개로 늘리면 비용도 두 배

### 방법 2. 자원 효율을 높인다

IO 대기로 인한 CPU 낭비를 줄이고, 요청 처리에 필요한 메모리를 줄이는 방향.

- **가상 스레드나 고루틴 같은 경량 스레드 사용**
- **논블로킹 또는 비동기 IO 사용**

두 방식을 적절히 사용하면 CPU와 메모리 자원을 늘리지 않고도 더 많은 트래픽을 처리할 수 있다. (→ 이 장에서 두 가지를 차례로 다룸)

> **주의**
성능을 높이겠다고 처음부터 비동기 IO로 개발하거나 가상 스레드를 적용하지는 말자.
> 
> 
> 실제로 IO 성능을 높여야 할 만큼 트래픽이 증가하고 있거나, 예상 트래픽이 높은 경우에만 적용 여부를 고민하자.
> 

# 가상 스레드로 자원 효율 높이기

---

## 1. 출발점: 블로킹 코드 그대로, 대기는 없애기

> 코드는 블로킹 IO로 작성했는데, 입출력 동안 스레드가 대기하지 않고 다른 일을 할 수 있다면?
> 

이게 가능하다면 **CPU의 유휴 시간이 줄고 더 많은 작업을 처리**할 수 있다. 

게다가 개발자는 성능을 높이기 위해 별도의 기술을 쓰지 않아도 된다.

이걸 가능하게 하는 것이 자바의 **가상 스레드**, Go 언어의 **고루틴**이다.

## 2. 경량 스레드란

언어는 다르지만 가상 스레드와 고루틴은 **경량(lightweight) 스레드**라는 공통점을 갖는다.

- 경량 스레드는 **OS가 관리하는 스레드가 아니라, JVM 같은 언어 런타임이 관리하는 스레드**다.
- OS가 CPU로 실행할 스레드를 스케줄링하듯, **언어 런타임이 OS 스레드로 실행할 경량 스레드를 스케줄링**한다.

!image.png

- **플랫폼 스레드** = OS 스레드에 1:1로 대응하는 래퍼
    - JVM은 플랫폼 스레드로 구성된 **풀**을 유지한다.
- CPU가 OS 스케줄러에 의해 여러 스레드를 번갈아 실행하듯, **플랫폼 스레드도 JVM 스케줄러에 의해 여러 가상 스레드를 번갈아 실행**한다.
- 기본적으로 풀에 **CPU 코어 개수만큼** 플랫폼 스레드를 생성하고, 필요에 따라 증가시킨다. (책 집필 시점 기준 최대 개수 기본값은 `256`)
    - 확인해보니 현재도 최대 개수 기본값이 256 JDK 21에서 가상 스레드가 정식 기능이 된 이후 바뀌지 않음

## 3. 왜 "경량"인가 : `자원 비교`

> **왜 가상 스레드를 경량 스레드로 부르는가? (요약)**
> 
> - 메모리 크기가 플랫폼 스레드의 1/300배이다
> - 스레드 생성 시간에도 1/100배 차이가 난다
> 
> ⇒ 즉, 가상 메모리는 **플랫폼 메모리에 비해 훨씬 적은 비용(자원,시간)**이 들기 때문에 한 장비에서 수십만에서 백만개에 이르는 가상 스레드를 생성할 수 있다
> 

### 1) 메모리

**플랫폼 스레드 1만 개** (기본 스택 크기 `1MB` 가정)

- `10,000MB` ≈ **9.8GB**
- 단, 이는 예약한(reserved) 메모리 기준이며 실제 사용(committed) 메모리는 이보다 작다. 그래도 상당량이 필요하다.

**가상 스레드 1만 개** (1개당 평균 `2KB` 가정)

- 힙 메모리 약 `20MB`
- 스케줄링용 플랫폼 스레드 8개 → 스택 메모리 `8MB`
- 합계 **28MB**

⇒ `9.8GB` vs `28MB`, **300배 넘게 차이**가 난다.

> **가상 스레드와 메모리**
가상 스레드는 수백 바이트에서 수 KB ~ 수십 KB의 힙 메모리를 사용한다.
**호출 스택의 깊이에 따라 사용하는 메모리를 동적으로 늘렸다 줄인다.** Go 언어의 고루틴도 동일한 방식으로 동작한다.
> 

### 2) 생성 시간

10만 개의 스레드를 생성하고 시작하는 데 걸린 시간(저자 노트북 기준 평균):

| 종류 | 소요 시간 |
| --- | --- |
| 플랫폼 스레드 | `21,467ms` |
| 가상 스레드 | `196ms` |

⇒ **100배 이상 차이**. 저자의 노트북에서 가상 스레드 100만 개는 생성할 수 있었지만, 플랫폼 스레드 100만 개 생성은 실패했다.

```java
// 가상 스레드는 Thread.ofVirtual()로 생성
Thread thread = Thread.ofPlatform().start(() -> {
    try {
        Thread.sleep(1000);
    } catch (InterruptedException e) {
        e.printStackTrace();
    }
});
```

⇒ 톰캣처럼 **요청별 스레드(thread per request)** 를 생성하는 서버에서 가상 스레드를 사용하면, **더 적은 메모리로 더 많은 요청을 처리**할 수 있다는 뜻이다.

## 4. 네트워크 IO와 가상 스레드

> **캐리어(carrier) 스레드**
가상 스레드를 실행하는 플랫폼 스레드를 캐리어 스레드라고 한다.
특정 가상 스레드가 특정 캐리어 스레드에 연결되는 것을 **마운트(mount)** 되었다고 표현한다. 마운트되면 가상 스레드가 실행되고, **언마운트(unmount)** 되면 실행을 멈춘다.
> 

핵심 동작: **가상 스레드가 실행 중 블로킹되면 플랫폼 스레드와 언마운트되고, 그 플랫폼 스레드는 실행 대기 중인 다른 가상 스레드와 연결되어 실행을 재개한다.**

!image.png

플랫폼 스레드 1은 가상 스레드 1을 실행하다가, 가상 스레드 1이 IO 대기 같은 블로킹 연산을 만나면 **그 블로킹이 끝나기를 기다리지 않고 실행 가능한 다른 가상 스레드를 찾아 연결**한다.

> **블로킹 연산과 `synchronized`**
블로킹 연산에는 IO 기능, `ReentrantLock`, `Thread.sleep()` 등이 포함된다. 이들 연산으로 가상 스레드가 블로킹되면 플랫폼 스레드는 대기 중인 다른 가상 스레드를 실행한다.
반면 **자바 23 또는 이전 버전에서 `synchronized`로 인해 블로킹되면 가상 스레드가 언마운트되지 않는다.** 즉, 플랫폼 스레드도 같이 블로킹된다. 이를 가상 스레드가 플랫폼 스레드에 **고정(pinned)** 됐다고 한다.
자바 21 기준으로 `synchronized` 외에 JNI 호출 등에서도 고정이 발생한다. **고정되면 CPU 효율을 높일 수 없으므로** 가상 스레드를 쓸 때 유의할 것.
> 

## 5. 가상 스레드, 언제 효과가 있나

코드는 크게 두 종류로 나뉜다.

| 구분 | 예시 |
| --- | --- |
| **IO 중심(IO-bound)** | 네트워크 프로그래밍처럼 **입출력이 주**를 이루는 작업 |
| **CPU 중심(CPU-bound)** | 정렬, 이미지 연산처럼 **계산이 주**를 이루는 작업 |

### 조건 1. IO 중심 작업이어야 한다

IO는 가상 스레드가 지원하는 블로킹 연산이므로, IO 중심 작업일 때 플랫폼 스레드가 CPU 낭비 없이 여러 가상 스레드를 실행할 수 있다.

반대로 **CPU 중심 작업에서는 효과가 없고, 오히려 나빠질 수도 있다.**

> 사용자가 업로드한 이미지의 썸네일을 생성하는 서버를 생각해보자.
> 
> 
> 이미지 연산 코드에는 **블로킹 연산이 없다.**
> 
> 블로킹 연산이 없으므로 연산이 끝날 때까지 플랫폼 스레드는 계속 1개의 가상 스레드만 실행하게 된다.
> 
> ⇒ 가상 스레드를 많이 생성해도 **동시 실행 효과를 얻을 수 없다.**
> 
- **블로킹 연산이 없는 코드**
    
    `썸네일 생성 코드 예시`
    
    ```java
    for (int y = 0; y < height; y++) {
        for (int x = 0; x < width; x++) {
            int rgb = source.getRGB(sx, sy);  // 메모리 읽기
            target.setRGB(x, y, blend(...));  // 계산 후 메모리 쓰기
        }
    }
    ```
    
    픽셀을 읽고 > 계산하고 > 쓰고 : CPU가 쉬지 않고 계속 일하는 코드 
    
    여기엔 `read()` 처럼 `DB야 결과 줄때까지 기다려` 하고 멈추는 구간이 없음
    
    ⇒ 가상 스레드는 스스로 비켜줘야 하는데, 위와 같은 블로킹 연산이 없는 코드는 스스로 비켜주지 않으니 연산이 끝날때까지 캐리어 스레드에서 내려오지 않음
    
    |  | 누가 스레드를 교체하나 | 계산만 하는 코드일 때 |
    | --- | --- | --- |
    | **플랫폼 스레드** | OS가 **선점형(preemptive)** 으로 강제 회수 | 타임 슬라이스마다 뺏겨서 다른 스레드도 실행됨 |
    | **가상 스레드** | 가상 스레드가 **스스로 양보**해야 함 | 양보 지점이 없어 계속 캐리어 점유 |

### 조건 2. 가상 스레드 개수 > 플랫폼 스레드 개수여야 한다

IO 중심 작업이라고 무조건 이점을 얻는 것은 아니다. 

**스케줄링에 사용되는 플랫폼 스레드보다 가상 스레드가 많아야** 효과를 기대할 수 있다.

**효과가 없는 예시**

- 장비 CPU 코어: 16개
- 서버의 평소 TPS: 500
- 1개 요청 처리 시간: 20ms
- 모든 요청은 IO 중심 작업

```
1 스레드 → 1초에 약 50개 요청 처리 (1000ms / 20ms)
500 TPS 처리에 필요한 스레드 = 500 / 50 = 10개
	→ 동시에 10개 요청만 처리하면 충분
```

- 플랫폼 스레드는 기본으로 **16개** 생성된다 (CPU 코어 개수)
- 동시 요청이 10개이므로 동시에 생성되는 가상 스레드는 **10개**
    - 이처럼 이런 상황에 가상 스레드를 사용하면, 플랫폼 스레드가 더 많이 생긴다 (10 < 16)

동시에 10개의 가상 스레드가 실행되지만 IO 중심 작업이라 대부분 IO 대기 상태에 있다. 플랫폼 스레드가 실행할 다른 가상 스레드를 찾아도 **대부분이 IO 대기 중이라 실행할 것이 없다.**

⇒ 결과적으로 플랫폼 스레드 16개 중 실제로 쓰이는 건 10개도 안 된다. **가상 스레드의 이점을 얻을 수 없다.**

**그럼 어떻게 해야 하나**

- **CPU 코어 수를 줄인다**: 클라우드에서 16코어 → 4코어로 줄이고 메모리도 줄여, **더 적은 비용으로 같은 트래픽 처리**
- **트래픽이 더 많아진다**: 동시에 필요한 스레드가 100개 → 1000개 이상이 될 정도로 증가하면 이점을 얻는다. 같은 CPU와 메모리로 **처리량을 10배** 늘릴 수 있다.

## 6. 가상 스레드의 가장 중요한 장점

**기존 코드를 크게 수정할 필요가 없다는 것.**

스프링 프레임워크나 MySQL JDBC 드라이버처럼 많이 쓰는 프레임워크·라이브러리도 이미 가상 스레드를 지원한다. 조금만 신경 쓰면 **기존 코드를 그대로 유지하면서** 서버 성능을 높일 수 있다.

# 논블로킹 IO로 성능 더 높이기

---

## 1. 왜 경량 스레드로 부족한가

경량 스레드를 쓰면 IO 중심 작업 서버의 처리량을 높일 수 있다. 

하지만 **경량 스레드 자체도 메모리를 사용하고 스케줄링이 필요하다.**

⇒ 경량 스레드가 많아질수록 더 많은 메모리를 쓰고, 스케줄링에 더 많은 시간을 쓴다.

사용자가 폭발적으로 증가하면 어느 순간 경량 스레드로도 한계가 온다. 이때는 서버의 IO 구현 방식을 **구조적으로 변경**해야 한다 ⇒  `논블로킹 IO`다.

**논블로킹 IO**는 **네트워크 서버의 성능을 높이기 위해 사용한 방식**이고, 여기에 **비동기 API를 곁들이면 덜 복잡한 코드로 높은 성능**을 낼 수 있다. 

**→ Nginx, Netty, Node.js** 등이 모두 논블로킹 IO를 사용한다.

## 2. 논블로킹 IO 동작 개요

논블로킹 IO는 **입출력이 끝날 때까지 스레드가 대기하지 않는다.**

```java
// channel: SocketChannel, buffer: ByteBuffer
int byteReads = channel.read(buffer); // 데이터를 읽을 때까지 대기하지 않음
...                                   // 읽은 데이터가 없어도 다음 코드 계속 실행
```

`channel.read()`는 **읽을 데이터가 없으면 바로 `0`을 리턴**한다. 데이터를 읽을 때까지 대기하는 블로킹 IO와는 동작 방식이 다르다.

|  | 블로킹 IO | 논블로킹 IO |
| --- | --- | --- |
| 읽을 데이터가 없을 때 | 데이터가 올 때까지 스레드 대기 | 즉시 `0` 리턴, 다음 코드 실행 |
| 코드 작성 전제 | "데이터를 조회했다"는 가정 하에 작성 가능 | 조회 여부를 매번 확인해야 함 |

### 순진하게 구현하면 CPU를 낭비한다

> **조회 여부를 확인하기 위해서 `무한 루프 + if(byteReads >0)` 인지 체크..?**
> 

```java
// CPU 낭비가 심한 방식
while (true) {
    int byteReads = channel.read(buffer);
    if (byteReads > 0) {
        handleData(channel, buffer);
    }
}
```

읽은 데이터가 없어도 `while` 루프가 무한히 실행된다. 

> 실제로는 **데이터 읽기를 바로 시도하기보다, 어떤 연산을 수행할 수 있는지 확인하고 해당 연산만 실행**하는 방식으로 구현한다.
> 

```
1. 실행 가능한 IO 연산 목록을 구한다 (구할 때까지 대기)
2. 구한 IO 연산 목록을 차례대로 순회한다
   A. 각 IO 연산을 처리한다
3. 반복
```

### Selector 기반 예제

```java
Selector selector = Selector.open();
ServerSocketChannel serverSocket = ServerSocketChannel.open();
serverSocket.bind(new InetSocketAddress(7031));
serverSocket.configureBlocking(false);                    // 서버 소켓 논블로킹 설정
serverSocket.register(selector, SelectionKey.OP_ACCEPT);  // 연결 연산 등록

while (true) {
    selector.select();  // 가능한 IO 연산이 있을 때까지 대기

    Set<SelectionKey> selectedKeys = selector.selectedKeys();
    Iterator<SelectionKey> iterator = selectedKeys.iterator();

    while (iterator.hasNext()) {              // IO 연산 순회
        SelectionKey key = iterator.next();
        iterator.remove();

        if (key.isAcceptable()) {             // 클라이언트 연결 처리가 가능하면
            SocketChannel client = serverSocket.accept();
            client.configureBlocking(false);  // 소켓 논블로킹 설정
            client.register(selector, SelectionKey.OP_READ); // 읽기 연산 등록

        } else if (key.isReadable()) {        // 읽기 연산이 가능하면
            SocketChannel channel = (SocketChannel) key.channel();
            int readBytes = channel.read(inBuffer);   // 채널에 읽기 연산 실행
            if (readBytes == -1) {
                channel.close();
                continue;
            }
            inBuffer.flip();
            outBuffer.put(inBuffer);          // 출력 버퍼에 복사
            outBuffer.flip();
            channel.write(outBuffer);         // 채널에 쓰기 연산 실행
            outBuffer.clear();
        }
    }
}
```

**핵심은 `Selector`다.**

- `Selector#select()`
    - **IO 처리가 가능한 연산이 존재할 때까지 대기**한다. 이 메서드가 리턴하면 수행할 수 있는 연산이 존재하는 것이다.
- `Selector#selectedKeys()`
    - 실행 가능한 연산 목록을 조회한다. 여기서 구한 `SelectionKey`로 어떤 연산이 가능한지 확인하고 해당 연산을 수행한다.

## 3. 블로킹 IO 구현과의 결정적 차이

> 블로킹 IO로 구현한 서버는 커넥션별로 스레드를 할당한다. 반면에 논블로킹 IO는 클라이언트 수에 상관없이 소수의 스레드만 사용한다.
> 

|  | 블로킹 IO | 논블로킹 IO |
| --- | --- | --- |
| 스레드 할당 | 커넥션별(또는 요청별)로 스레드 할당 | 클라이언트 수와 무관하게 **소수의 스레드** 사용 |
| 동시 연결 1,000개면 | 스레드 1,000개 생성 | 위 예제 기준 **스레드 1개** |
| 접속자 증가 시 | 스레드 수 함께 증가 → 메모리 증가 | 스레드 개수는 **일정하게 유지** |

⇒ **같은 메모리로 훨씬 더 많은 클라이언트 연결을 처리**할 수 있다.

## 4. 동시성 높이기 — 스레드를 N개로

논블로킹 IO를 **1개 스레드로 구현하면 동시성이 떨어진다.** 앞 예제 기준으로, 1개 채널의 읽기 처리가 끝나야 다음 채널의 읽기 처리를 실행한다. 두 채널의 읽기 연산이 모두 가능해도 한 번에 1개만 처리된다.

!image.png

```
스레드 1 ── 읽기 연산 · 읽기 연산
스레드 2 ── 쓰기 연산 · 읽기 연산 · 연결 연산
스레드 3 ── 읽기 연산 · 읽기 연산 · 쓰기 연산 · 읽기 연산
```

⇒ **채널들을 N개 그룹으로 나누고, 각 그룹마다 스레드를 생성**한다. 보통 **CPU 개수만큼** 그룹을 나누고 각 그룹에 입출력 처리 스레드를 할당한다.

## 5. 리액터 패턴

논블로킹 IO로 구현할 때 사용하는 패턴 중 하나. 

동시에 들어오는 여러 이벤트를 처리하기 위한 **이벤트 처리 방법**이며, 두 요소로 구성된다.

| 요소 | 역할 |
| --- | --- |
| **리액터(Reactor)** | 이벤트가 발생할 때까지 대기하다가, 발생하면 알맞은 핸들러에 이벤트를 전달 |
| **핸들러(Handler)** | 전달받은 이벤트에 대해 필요한 로직을 수행 |

```java
while (isRunning) {
    List<Event> events = getEvents();          // 이벤트가 발생할 때까지 대기
    for (Event event : events) {
        Handler handler = getHandler(event);   // 이벤트를 처리할 핸들러 구함
        handler.handle(event);                 // 이벤트를 처리함
    }
}
```

리액터는 **이벤트 대기 → 핸들러 전달**을 반복하므로 **이벤트 루프(event loop)** 라고도 한다.

앞서 본 `Selector` 예제의 구조와 비교하면, **`SelectionKey`를 이벤트에 대응시키면 리액터 패턴과 처리 방식이 완전히 동일**하다. 실제로 Netty, Nginx, Node.js 등이 리액터 패턴을 적용하고 있다.

### 이벤트 루프의 한계와 보완

리액터 패턴에서 이벤트 루프는 **단일 스레드로 실행된다.** 여기서 두 가지 문제가 생긴다.

- 멀티코어 서버에서 단일 스레드만 쓰면 처리량을 최대한 낼 수 없다.
- 핸들러에서 **CPU 연산이나 블로킹 연산을 수행하면 그 시간만큼 전체 이벤트 처리가 지연된다.**

⇒ 핸들러나 블로킹 연산을 별도 스레드 풀에서 실행해 보완한다.

| 프레임워크 | 보완 방식 |
| --- | --- |
| **Netty** | 여러 개의 이벤트 루프를 생성해 멀티코어 활용 |
| **Node.js** | 이벤트 루프 외에 별도 스레드 풀을 사용해 CPU 중심 작업·블로킹 연산 처리 |

## 6. 프레임워크 사용하기

줄 단위로 데이터를 수신하는 서버를 구현한다고 해보자.

**블로킹 IO** — `BufferedReader`로 쉽게 읽는다.

```java
BufferedReader br = new BufferedReader(
        new InputStreamReader(socket.getInputStream(), "UTF-8"));
String line;
while ((line = br.readLine()) != null) { // 줄 단위로 쉽게 읽을 수 있음
    // line 처리
}
```

**논블로킹 IO** — 직접 구현하면 처리가 복잡해진다.

- 데이터를 읽은 뒤 `\n` 문자가 있는지 확인해야 한다.
- `\n`이 없으면 읽은 데이터를 별도 버퍼에 계속 누적해야 한다.
- `\n`이 여러 개 존재하는 경우도 처리해야 한다.
- 채널마다 누적 처리를 위한 버퍼도 관리해야 한다.

⇒ **주고받는 데이터 형식이 조금만 바뀌어도 저수준 IO 처리 코드를 변경**해야 한다. 그래서 논블로킹 IO API를 직접 쓰기보다 **프레임워크를 사용하는 것을 선호**한다.

**리액터 네티(Reactor Netty)로 구현한 줄 단위 에코 서버**

```java
DisposableServer server = TcpServer.create()
        .port(7031)
        .doOnConnection(conn ->
                conn.addHandlerFirst(new LineBasedFrameDecoder(1024))) // 줄 단위 읽기 처리
        .handle((in, out) ->
                in.receive()
                  .asString()                    // byte를 문자열로 변환
                  .doOnNext(line -> log.info("received: {}", line))
                  .flatMap(line ->
                          out.sendString(Mono.just(line + "\n")))  // 문자열 쓰기
        )
        .bindNow();
```

리액터 네티가 줄 단위 읽기와 문자열 변환을 제공하므로 저수준 IO 처리를 직접 구현하지 않아도 된다. 리액티브 API(스프링 리액터)를 익혀야 하지만, 익숙해지면 논블로킹 IO API를 직접 쓰는 것보다 **간단한 코드로 논블로킹/비동기 IO 방식을 구현**할 수 있다.

## 7. 논블로킹/비동기 IO와 성능 — 저자의 측정 결과

**자바 푸시 서버 (JVM 힙 메모리 `1.5G` 할당 기준, 최대 동접 수)**

| 방식 | 최대 동접 수 |
| --- | --- |
| 블로킹 IO | 약 `6,000` |
| 논블로킹 IO | 약 `120,000` |

⇒ 약 **20배** 향상

**Go 언어 (메모리 사용량 `500MB` 기준, 최대 동접 수)**

| 방식 | 최대 동접 수 |
| --- | --- |
| 클라이언트별 고루틴 | 약 `20,000` |
| gnet (논블로킹/비동기 IO) | 약 `180,000` |

⇒ 약 **9배** 차이

**경량 스레드보다도 논블로킹 IO가 더 많은 동접을 처리**한다는 점이 핵심이다. 

# 언제 어떤 방법을 택할까

---

 논블로킹 IO나 가상 스레드를 적용할 때는 먼저 다음 세 가지를 순서대로 검토해야 한다.

```
1. 문제가 있는가?
     ↓ 있다
2. 그 문제가 네트워크 IO 관련 성능 문제인가?
     ↓ 그렇다
3. 구현 변경이 가능한가?
     ↓ 가능하다
   → 변경을 시도하자
```

## 1. 문제가 있는가

가장 먼저 검토할 점은 **성능 문제가 실제로 있는지 여부**다.

- 성능 문제가 없다면
- 또는 당분간 트래픽 증가 가능성이 없다면

⇒ 논블로킹 IO나 가상 스레드를 검토할 필요가 **없다.** 문제가 없는데 구현을 변경하는 것은 시간 낭비다.

게다가 논블로킹/비동기 IO로 구현하면 **코드가 복잡해지고 유지보수 난이도도 올라간다.**

> 단순한 호기심으로 안 해도 되는 구현 변경을 시도하지는 말자.
**성능 문제가 전혀 없는데 성능을 높이겠다며 복잡하게 구현하지 말자.**
> 

## 2. 네트워크 IO 관련 문제인가

성능 문제가 있다면, 그 문제가 **네트워크 IO와 관련된 자원 문제인지** 확인해야 한다.

**해당하지 않는 사례**

| 상황 | 왜 효과가 없나 | 올바른 해법 |
| --- | --- | --- |
| 트래픽은 그대로인데 DB 쿼리가 느려져 응답 시간이 길어짐 | 가상 스레드·논블로킹 IO는 **응답 시간을 줄이지 못한다** | 쿼리 최적화, 캐시 도입 |
| 썸네일 생성 같은 CPU 중심 작업 | 이미지 처리 과정에는 블로킹 IO가 없으므로 **처리 시간이 줄지 않는다** | CPU 자원 확보, 작업 분리 |

⇒ 앞 절에서 정리한 **"높아지는 것은 처리량이지 속도가 아니다"** 가 여기서 판단 기준으로 작동한다.

## 3. 구현 변경이 가능한가

문제가 IO 관련이라면, 그때는 구현 변경이 가능한지를 따져야 한다.

**변경이 가능한 경우**

> 동시 요청 클라이언트가 늘면서 실행 스레드 수도 많아졌고, 그 결과 **메모리 사용률이 98%까지** 올라갔다. 이 상황이 지속되면 장애가 발생할 수 있다.
⇒ 가상 스레드를 적용할 수 있다면, **적용하는 것만으로 메모리 사용률을 줄일 수 있다.**
⇒ 적용할 수 없다면 일단 메모리를 늘리거나 서버를 수평 확장해 문제를 완화하는 수밖에 없다.
> 

**변경이 불가능한 경우 — 우선순위**

신기능 개발에 많은 인력이 투입된 상황이라면 성능 개선에 쓸 인력이 없을 수도 있다. 이럴 때는 구현 방식을 바꾸는 대신 **서버 확장으로 해결**하고, 이후 여유가 생기면 성능 개선을 진행한다.

**변경이 불가능한 경우 — 기술에 대한 익숙함**

웹소켓 서버의 동시 접속자가 증가해 성능 문제가 발생했다고 하자. 논블로킹 IO를 적용하면 효과를 볼 수 있지만, **개발자가 관련 기술을 모르면 성능 개선은 어렵다.**

## 정리

> **문제가 있고**, 그 문제가 **네트워크 IO와 관련**되어 있으며, **구현 변경이 가능한 상황**이라면 변경을 시도하자.
그러면 **성능 개선이라는 결과**와 **새로운 기술을 적용하는 재미(?)**를 모두 얻을 수 있다
>
