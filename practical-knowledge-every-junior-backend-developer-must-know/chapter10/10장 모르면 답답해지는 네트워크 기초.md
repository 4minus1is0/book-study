## 이 장을 한 줄로

> **서버가 "왜 연결이 안 되는지" 모를 때, 코드가 아니라 네트워크를 봐야 하는 순간이 온다.**
`노드 → 라우터 → IP/도메인 → NAT → VPN → 프로토콜` 순서로, 패킷이 내 서버까지 도달하는 경로를 한 번에 훑는 장.

## 10.1 네트워크 기초를 모르면

책은 저자가 겪은 사례로 시작한다. 외부 업체 API에 연결이 안 되는 문제였는데,

- 코드에 적힌 API 주소 → 정상
- 방화벽 아웃바운드 설정 → 정상
- 업체 측 인바운드 허용 정책 → 정상

셋 다 이상이 없었다. 원인은 **접속 허용을 요청할 때 알려준 IP가 틀렸던 것**이었다.
서버에는 공인 IP가 두 개 물려 있었는데, 하나는 *외부에서 서버로 들어올 때* 쓰는 IP이고 다른 하나는 *서버에서 외부로 나갈 때* 쓰는 IP였다. 업체에는 후자를 알려줬어야 했는데 전자를 알려준 것.

> 🔑 이 사례는 10.4 NAT 절과 이어진다. 나가는 패킷의 출발지 주소를 바꾸는 게 SNAT, 들어오는 패킷의 목적지 주소를 바꾸는 게 DNAT다. **들어오는 IP와 나가는 IP는 다를 수 있다**는 사실 자체가 NAT 때문에 생긴다.
> 

네트워크 엔지니어만큼 깊이 알 필요는 없지만, 기초를 모르면 이런 문제 하나에 며칠을 쓰게 된다는 것이 이 장의 출발점이다.

## 10.2 노드, 네트워크, 라우터

### 용어 정리

| 용어 | 정의 |
| --- | --- |
| **노드(node)** | 데이터를 송수신하는 모든 장치. 휴대폰, 노트북, 서버 장비 등 |
| **네트워크(network)** | 노드들이 서로 데이터를 주고받기 위해 연결된 시스템 |
| **라우터(router)** | 서로 다른 네트워크 사이에서 패킷을 전달하는 장치 |
| **패킷(packet)** | 네트워크로 전송되는 데이터의 단위. `헤더`(발신자·수신자 정보) + `페이로드`(실제 데이터) |

!image.png

집 공유기에 붙어 있는 휴대폰·노트북·TV가 하나의 네트워크를 이루고, 사무실 PC들이 또 하나의 네트워크를 이룬다. 데이터는 통째로 가지 않고 **일정 크기의 패킷으로 쪼개져** 전송된다.

### 서로 다른 네트워크는 직접 못 만난다

내 휴대폰과 내가 호출하는 API 서버는 **서로 다른 네트워크**에 속한다. 다른 네트워크의 노드끼리는 직접 연결해서 패킷을 주고받을 수 없고, 이때 중간에서 패킷을 넘겨주는 것이 라우터다. 실제 요청 하나가 서버까지 가는 동안 **여러 대의 라우터를 거친다.**

!image.png

서울에서 부산 가는 길이 여러 갈래인 것처럼, 두 노드 사이의 경로도 하나가 아니다. 각 라우터는 목적지 주소를 보고 **다음에 넘길 라우터를 스스로 고른다.**

## 10.3 IP 주소와 도메인

### IP 주소

택배를 보내려면 주소가 필요하듯, 패킷을 보내려면 노드의 주소가 필요하다. 그 주소가 **IP 주소**다.

- 지금 일반적으로 쓰는 것은 **IPv4** (`v4` = 버전 4)
- 1바이트(8비트) 숫자 블록 4개로 구성 → 각 블록은 `0 ~ 255`
- 예: `223.130.192.248`

> **📌 IPv6는 왜 아직 안 쓰이나**
> 
> - IPv4는 32비트 → 고유 주소가 약 **43억 개**. 1990년대 초부터 이미 고갈이 예상됐다.
> - 그래서 나온 것이 **IPv6(128비트)**. 전 세계 모든 기기에 고유 주소를 주고도 남을 양이다.
> - 2000년대 초반엔 곧 IPv6로 넘어갈 거라는 전망이 많았지만, 지금도 대부분 IPv4를 쓴다.
> - **고갈되지 않은 이유가 바로 사설 IP와 NAT** (10.3 후반부 + 10.4에서 이어짐).

### 도메인과 DNS

IP 주소는 외우기 어렵다. 그래서 기억하기 쉬운 이름을 붙인 것이 **도메인 이름**이고, 도메인 이름과 IP 주소를 서로 변환해주는 체계가 **DNS(Domain Name System)** 다. 책은 DNS를 *인터넷 전화번호부*에 비유한다.

**도메인은 계층 구조다.** 점(`.`)으로 구분하며 **오른쪽이 상위, 왼쪽이 하위**다.

```
cafe . naver . com
 3차    2차    최상위(TLD)
 ←── 하위        상위 ──→
```

| 구분 | 최상위 예시 | 주요 이름이 오는 위치 |
| --- | --- | --- |
| 일반 최상위 도메인 | `com` `org` `net` `gov` `app` `biz` `tech` | **2차** — `naver.com`, `google.com` |
| 국가 최상위 도메인 | `kr` `jp` `au` | **3차** — `gasapp.co.kr` |

국가 최상위 도메인은 두 번째 계층이 용도별로 미리 정해져 있다. `ac.kr`은 대학 같은 교육기관, `co.kr`은 기업용이다. 그래서 주요 이름이 한 계층 밀려 3차에 온다.

!image.png

흐름을 정리하면:

```
브라우저 ──① www.naver.com의 IP 문의──▶ DNS 서버
브라우저 ◀──② 223.130.192.248 응답──── DNS 서버
브라우저 ──③ 해당 IP로 데이터 전송───▶ 서버
```

- `localhost`는 특별한 주소로, 대응하는 IP는 **`127.0.0.1`(루프백 주소)** 이며 **자기 자신**을 가리킨다.

> **📌 hosts 파일 — DNS보다 먼저 본다**
> 
> - 위치: 리눅스 `/etc/hosts`, 윈도우 `C:\Windows\System32\drivers\etc`
> - 호스트 이름과 IP의 매핑을 직접 정의하는 파일이다.
> - **DNS 서버보다 hosts 파일의 매핑이 우선한다.** `localhost` 매핑도 여기 정의돼 있다.
> - 로컬 개발에서 가짜 도메인을 붙여 테스트할 때 쓰는 이유가 이것.

> **📌 도메인 하나에 IP는 여러 개일 수 있다**
> 
> - `nslookup <도메인>` 을 실행해보면 IP가 여러 개 나오는 경우가 있다.
> - 이유 중 하나는 **부하 분산**이다. DNS 서버가 등록된 IP들을 번갈아 응답해주면, 요청이 여러 서버로 나눠진다.
>     
>     !image.png
>     

### 고정 IP와 동적 IP

|  | 고정 IP | 동적 IP |
| --- | --- | --- |
| 방식 | 노드에 IP를 직접 지정 | 네트워크에 연결할 때마다 할당받음 |
| 할당 주체 | 사람이 설정 | **DHCP 서버** |
| 대표 사례 | 서버 (IP가 바뀌면 안 되므로) | 가정용 공유기 환경 |

DHCP(Dynamic Host Configuration Protocol) 서버는 IP 주소만 주는 게 아니라, 인터넷에 연결하는 데 필요한 **게이트웨이 주소 · 서브넷 마스크 · DNS 서버 주소**까지 함께 내려준다.

> 💡 **동적 IP = 매번 바뀌는 IP가 아니다.** DHCP 설정에 따라 일정 시간 동안은 같은 IP를 계속 준다. 보안이 중요한 환경에서는 IP로 사용자를 식별하려고 노드마다 IP를 고정 할당하기도 한다.
> 

### 공인 IP와 사설 IP

|  | 공인(public) IP | 사설(private) IP |
| --- | --- | --- |
| 적용 범위 | 모든 네트워크 (공용 주소) | 특정 네트워크 내부 |
| 인터넷에서 접근 | 가능 (방화벽으로 막지 않았다면) | **불가능** |
| 주소 중복 | 불가 — 전 세계에서 유일 | **가능** — 네트워크가 다르면 같아도 됨 |
| 예 | 홈페이지, 공개 API 서버 | 공유기에 붙은 휴대폰·노트북·태블릿 |

**사설 IP로 쓸 수 있는 대역은 세 개로 정해져 있다.**

```
192.168.x.x
10.x.x.x
172.16.x.x ~ 172.31.x.x
```

집·카페의 무선 공유기는 보통 `192.168` 대역을 쓴다. 지금 내 노트북이 어떤 IP를 쓰는지는 `ifconfig`(리눅스/맥) 또는 `ipconfig`(윈도우)로 확인할 수 있고, 대부분 위 세 대역 중 하나가 찍힌다.

!image.png

카페 공유기에서 받은 사설 IP와 집 공유기에서 받은 사설 IP가 같아도 충돌하지 않는다. **사설 IP는 그 네트워크 안에서만 고유하면 되기 때문**이다.

> 🔑 인터넷 초창기엔 회사의 PC마다 공인 IP를 할당하기도 했다. 모든 기기가 그렇게 했다면 IPv4는 진작 고갈됐을 것이다. 지금은 서버 네트워크·회사·가정 대부분이 사설 IP를 쓰고, **인터넷에 서비스를 제공해야 하는 대상에만 공인 IP를 쓴다.**
>

## 10.4 NAT

**NAT(Network Address Translation, 네트워크 주소 변환)** 는 말 그대로 네트워크 주소를 바꿔주는 기술이다. 내부에서 쓰는 사설 IP와 인터넷에서 쓰는 공인 IP 사이의 변환을 담당하며, 주로 **라우터 같은 네트워크 장비**가 수행한다.

### SNAT — 나갈 때

내부 네트워크에서 **나가는 패킷의 출발지(Source) 사설 IP를 공인 IP로 바꾸는 것**.

!image.png

```
휴대폰(192.168.1.10) ──▶ 공유기/라우터 ──[출발지를 218.39.xx.xxx로 변환]──▶ 인터넷
```

### DNAT — 들어올 때

공인 IP로 **들어온 패킷의 목적지(Destination)를 내부 사설 IP로 바꾸는 것**.

!image.png

```
클라이언트 ──▶ 네트워크 장비(58.221.x.x) ──[10.1.1.101로 변환]──▶ 서버 1(10.1.1.101)
                                                          서버 2(10.1.1.102)
```

**DNAT는 서버를 구성할 때 쓰인다.** 보안과 이중화를 고려하면 서버 노드는 공인 IP가 아니라 사설 IP를 갖는 게 낫다. 그래서 공인 IP는 연결을 관리하는 장비(라우터, 방화벽 등)에만 할당하고, 그 장비가 DNAT로 내부 서버에 패킷을 넘긴다.

> 📌 내 공인 IP 확인하기
> 
> 
> SNAT로 변환된 뒤의 공인 IP는 스스로는 알 수 없다. 공인 IP를 알려주는 서비스에 접속해서 확인한다.
> 
> ```bash
> curl ifconfig.me
> ```
> 
> 브라우저로 해당 주소에 접속해도 된다.
> 

> 🔑 **10.1의 사례가 여기서 풀린다.** 서버가 밖으로 나갈 때 보이는 IP(SNAT 결과)와 외부에서 서버로 들어올 때 쓰는 IP(DNAT 대상)는 서로 다른 주소일 수 있다. 방화벽 허용 요청을 할 땐 **"나가는 IP"** 를 알려줘야 한다.
>

## 10.5 VPN

### 문제 상황

백엔드 서버를 개발·운영하다 보면 서버 노드에 SSH로 접속하거나 DB에 붙어 SQL을 실행해야 할 일이 생긴다. 그런데 **서버 네트워크에는 허용된 사람만 들어올 수 있어야 한다.**

!image.png

서버 네트워크의 노드는 사설 IP를 쓰므로 외부에서 직접 접근할 수 없다. NAT를 쓰면 공인 IP를 통해 접근할 수는 있지만,

- 노드가 많으면 사설 IP마다 공인 IP를 매핑하는 것 자체가 어렵고,
- 설사 가능하더라도 **서버 네트워크의 모든 노드가 공인 IP로 노출되어 보안 문제가 생긴다.**

### 해결책: VPN

**VPN(Virtual Private Network, 가상 사설 네트워크)** 은 인터넷 같은 **공용 네트워크 위에서, 서로 다른 두 네트워크 사이에 암호화된 연결을 제공**한다. 두 네트워크가 마치 하나의 사설 네트워크에 있는 것처럼 연결되므로, 개발자는 안전하게 서버 네트워크에 접근할 수 있다.

!image.png

```
사무실 네트워크 ─ VPN 장비 ══[통신 암호화]══ VPN 장비 ─ 서버 네트워크(서버1/서버2/DB)
```

집이나 카페 같은 외부 공간에서는 **전용 VPN 클라이언트**를 통해 VPN에 접근한다.

!image.png

## 10.6 프로토콜과 TCP, UDP, QUIC

**프로토콜(protocol)** 은 네트워크상에서 두 노드가 데이터를 주고받기 위해 정한 규칙이다. 네트워크는 여러 계층으로 구성되고, **계층마다 사용하는 프로토콜이 따로 있다.**

!image.png

| 계층 | 주요 프로토콜 |
| --- | --- |
| 애플리케이션(application) | HTTP, FTP, SMTP |
| 전송(transport) | **TCP, UDP** |
| 네트워크(network) | IP |
| 데이터 링크(data link) | — |
| 물리(physical) | — |

> 💡 TCP/IP 모델은 **애플리케이션 / 전송 / 인터넷 / 네트워크 인터페이스**의 4계층으로도 표현한다. 위 5계층은 네트워크 인터페이스 계층을 데이터 링크와 물리로 나눠 그린 것이다.
> 

개발자가 실제로 다루는 건 주로 **전송 계층과 애플리케이션 계층**이다.

### TCP — 연결하고 보낸다

**TCP(Transmission Control Protocol)** 는 **연결 기반** 프로토콜이다. 전화를 걸어 상대가 받은 뒤에 대화하는 것처럼, 두 노드가 먼저 연결을 맺고 데이터를 주고받는다. 이 연결 과정을 **3-Way Handshake**라고 부른다.

!image.png

```
클라이언트 ──── SYN ────▶ 서버
클라이언트 ◀── SYN-ACK ── 서버
클라이언트 ──── ACK ────▶ 서버
             연결 완료 → 데이터 송수신
```

**장점 — 신뢰성**

- 패킷의 **순서를 보장**한다.
- 패킷이 **유실되면 재전송**한다.
- 그래서 애플리케이션 계층의 HTTP, SMTP 같은 많은 프로토콜이 TCP 위에서 동작한다.

**단점 — 속도**

- 시퀀스 번호, 확인 응답, 재전송 같은 장치가 붙으면서 UDP 대비 **상대적으로 느리다.**
- **HOL 블로킹(Head-of-Line Blocking)**: 앞선 패킷 하나가 유실되면, 그 패킷이 도착할 때까지 뒤에 온 패킷들을 제때 처리하지 못한다. 결과적으로 **전체 전송 속도가 느려진다.**

### UDP — 그냥 보낸다

**UDP(User Datagram Protocol)** 는 연결 과정 없이 바로 데이터를 보낸다.

- 정상적으로 전송됐는지 **알 수 없고**, 순서도 **보장하지 않는다.**
- → 애플리케이션이 **"데이터가 유실될 수 있다"는 전제로** 개발돼야 한다.
- 응답 확인·패킷 정렬 과정이 없으니 **TCP보다 빠르다.**
- 사용처: **DNS, VoIP, 게임** — 속도가 중요하거나 일부 유실이 치명적이지 않은 통신.

### QUIC — 빠르면서 신뢰성도

> TCP는 신뢰성이 있지만 느리고, UDP는 빠르지만 신뢰성이 없다. **둘 다 가지면 안 되나?** → 그 목적으로 만들어진 것이 **QUIC**.
> 

QUIC은 **UDP를 기반으로 하되, TCP가 해주던 일을 QUIC 계층에서 직접 처리**한다.

| 기능 | QUIC의 처리 방식 |
| --- | --- |
| 연결 관리 | 데이터에 **연결 ID(Connection ID)** 를 포함시켜 두 노드 간 연결을 유지 |
| 혼잡 제어 · 패킷 유실 복구 | QUIC 프로토콜 수준에서 제어 |
| 암호화 | **TLS를 통합** — QUIC 패킷은 기본적으로 암호화되어 전송 |
| 멀티플렉싱 | 한 연결에서 여러 스트림을 동시 처리 |

**① 핸드셰이크가 짧다**
TCP 기반 HTTPS는 `TCP 3-Way Handshake` → `TLS Handshake`를 차례로 진행해야 연결이 수립된다. QUIC은 TLS를 통합해 이 과정을 **한 번으로 단축**했다.

**② HOL 블로킹을 스트림 단위로 격리한다**
QUIC은 한 연결에서 여러 스트림을 동시에 처리하므로, **한 스트림에 HOL 블로킹이 생겨도 다른 스트림은 영향을 받지 않는다.**
참고로 **HTTP/2도 멀티플렉싱을 지원하지만, TCP 자체에서 발생하는 HOL 블로킹은 피할 수 없다.** QUIC이 UDP 기반인 이유가 여기 있다.

!image.png

```
HTTP/2, HTTP/1.1        HTTP/3
      TLS            QUIC (TLS 통합)
      TCP                 UDP
      IP                   IP
```

**③ 이미 쓰이고 있다**

- 브라우저: 크롬, 엣지, 사파리 등 주요 브라우저가 HTTP/3 지원
- 서비스: 구글, 페이스북 등
- CDN: 아카마이, 클라우드플레어, AWS 클라우드프론트 등
- 국내 기업도 HTTP/2를 넘어 HTTP/3 지원이 늘어나는 추세

**확인 방법**: 브라우저 개발자 도구 Network 탭의 **Protocol 값이 `h3`** 이면 HTTP/3로 통신한 것이다.

> **📌 TCP 연결은 65,535개가 한계인가?**
> 
> 
> **결론: 아니다.** 포트 번호가 16비트라 최대값이 65535일 뿐, 그것이 연결 개수의 한계는 아니다.
> 
> TCP의 각 연결은 아래 **4개 값의 조합**으로 구분된다.
> 
> ```
> (로컬 IP, 로컬 포트, 원격 IP, 원격 포트)
>    32비트    16비트    32비트    16비트
> ```
> 
> 로컬 IP가 고정돼 있을 때 이론적으로 가능한 연결 수는:
> 
> ```
> 2^16(로컬포트) × 2^32(원격IP) × 2^16(원격포트) = 2^64  (약 1,844경)
> ```
> 
> **65,535라는 숫자의 정확한 의미**는 → *하나의 로컬 IP에서 **특정 원격 IP의 특정 포트 1개**에 맺을 수 있는 연결 수*다.
> 
> 물론 이론값일 뿐이고, 실제 생성 가능한 연결 수는 **OS 설정(파일 디스크립터 개수, 포트 범위 설정 등)** 에 따라 제약을 받는다.
>

## 정리 — 요청 하나가 서버에 닿기까지

```
브라우저
  │ ① 도메인 → IP  (hosts 파일 먼저 확인 → 없으면 DNS 질의)
  ▼
내 노드 (사설 IP · DHCP로 할당받음)
  │ ② 공유기에서 SNAT — 출발지를 공인 IP로 변환
  ▼
여러 라우터를 경유 (목적지 IP 보고 다음 홉 선택)
  │ ③ 서버 측 방화벽/라우터에서 DNAT — 목적지를 사설 IP로 변환
  ▼
서버 노드 (사설 IP)
  │ ④ 전송 계층: TCP(3-Way Handshake) 또는 UDP / QUIC
  ▼
애플리케이션 계층: HTTP
```

### 백엔드 관점 체크리스트

- [ ]  서버 노드에 공인 IP를 직접 붙이지 않고, 앞단 장비 + DNAT 구조로 가고 있는가?
- [ ]  운영 서버 접근은 VPN 등 통제된 경로로만 열려 있는가?
- [ ]  로컬 테스트에서 도메인이 이상하게 풀린다면 → **hosts 파일**을 의심했는가?
- [ ]  DNS 응답 IP가 매번 다르다면 → 장애가 아니라 **부하 분산**일 수 있다.
- [ ]  "커넥션 65,535개 한계"라는 말을 들었을 때, 그게 **어떤 단위의 한계인지** 되물을 수 있는가?

- DNS 응답은 어디에 얼마나 캐싱되는가? (브라우저 / OS / 리졸버 각각의 TTL) — 배포 후 도메인 변경이 바로 반영되지 않는 이유와 연결
- SNAT 환경에서 라우터는 **응답 패킷을 어떻게 원래 내부 노드로 되돌려 보내는가?** (포트 기반 매핑 테이블 = PAT)
- TCP HOL 블로킹은 **정확히 어느 계층의 버퍼에서** 발생하는가? HTTP/2 멀티플렉싱이 이를 못 피하는 구조적 이유
- QUIC이 UDP 위에서 재전송·순서 보장을 다시 구현했다면, **TCP를 고치는 대신 UDP 위에 새로 만든 이유**는? (미들박스 문제)
- 커넥션 풀 크기를 정할 때 실제로 걸리는 상한은 무엇인가? (포트 범위 · 파일 디스크립터 · TIME_WAIT) — 2장 커넥션 풀 내용과 연결
