## 5.1 동기 연동과 비동기 연동

### 동기 방식

동기 방식은 한 작업이 끝난 뒤 다음 작업을 실행한다. 코드의 작성 순서와 실행 순서가 같아 흐름을 이해하고 디버깅하기 쉽다.

```java
public boolean login(String id, String password) {
    Optional<User> optionalUser = findUser(id);

    if (optionalUser.isEmpty()) {
        return false;
    }

    User user = optionalUser.get();

    if (!user.matchesPassword(password)) {
        return false;
    }

    PointResult result = pointClient.giveLoginPoint(id);

    if (result.isFailed()) {
        throw new PointException();
    }

    appendLoginHistory(id);
    return true;
}
```

로그인 예시는 사용자 조회, 비밀번호 확인, 포인트 지급, 로그인 내역 기록 순서로 실행된다. 포인트 지급이 끝나야 다음 작업으로 넘어간다.

![포인트 지급을 실행한 뒤 로그인 내역을 기록하는 동기 방식 .png](5장 사진/포인트 지급을 실행한 뒤 로그인 내역을 기록하는 동기 방식.png)

외부 서비스와 동기 연동할 때는 외부 연동 실패가 전체 기능의 실패로 이어져도 되는지, 외부 서비스의 지연을 기다려도 되는지 확인해야 한다.

### 동기 연동의 문제

포인트 지급 실패가 로그인 실패로 이어지면 포인트 서비스 장애 때문에 로그인까지 막힌다. 실패 내역을 남겨 후처리할 수 있지만, 여전히 외부 서비스의 응답은 기다려야 한다.

```java
PointResult result = pointClient.giveLoginPoint(id);

if (result.isFailed()) {
    recordPointFailure(id, result);
}
```

> 다음 작업에 외부 연동 결과가 반드시 필요하지 않다면 비동기 연동을 검토할 수 있다.

---

### 비동기 방식

비동기 방식은 한 작업이 끝날 때까지 기다리지 않고 다음 작업을 실행한다. 포인트 지급을 비동기로 처리하면 로그인 서비스는 지급 결과를 기다리지 않고 로그인 성공을 응답할 수 있다.

![별도 스레드를 이용해 포인트 지급을 비동기로 처리하는 방식.png](5장 사진/별도 스레드를 이용해 포인트 지급을 비동기로 처리하는 방식.png)

포인트가 조금 늦게 지급돼도 문제가 없다면 응답 속도를 높이고 외부 서비스의 지연과 장애가 핵심 기능으로 전파되는 것을 줄일 수 있다.

---

## 비동기 연동을 적용할 수 있는 경우

다음 조건 중 일부를 만족한다면 비동기 연동을 검토할 수 있다.

### 1. 처리에 약간의 시차가 생겨도 되는 경우

주문 알림, 포인트 지급, 검색 서비스 반영처럼 처리가 조금 늦어도 핵심 기능에 문제가 없는 경우다.

### 2. 실패했을 때 재시도할 수 있는 경우

푸시 전송이나 포인트 지급처럼 일시적 실패 후 다시 처리할 수 있는 경우다.

### 3. 나중에 수동으로 처리할 수 있는 경우

검색 서비스 등록 실패처럼 관리 도구로 다시 처리할 수 있는 경우다.

### 4. 실패를 무시해도 되는 경우

주문 알림처럼 실패하더라도 주문 자체에는 영향을 주지 않는 경우다.

- 주문 정보 동기화
- 택배사 집하 요청
- 주문 완료 알림
- 검색 인덱스 갱신

1. 별도 스레드로 실행하기
2. 메시징 시스템 이용하기

## 핵심 정리

> 외부 연동 결과가 현재 작업을 완료하는 데 반드시 필요하지 않고, 지연·재시도·수동 복구를 허용할 수 있다면 비동기 연동을 고려한다.

비동기 연동의 핵심은 핵심 기능과 부가 기능을 분리해 외부 서비스의 지연과 장애가 전체 서비스로 전파되는 것을 줄이는 데 있다.

## 5.2 별도 스레드로 실행하기

별도 스레드는 비동기 연동을 구현하는 가장 간단한 방법이다. 주문 처리와 푸시 발송을 분리하면 푸시 발송을 기다리지 않고 주문 결과를 반환할 수 있다.

### 새로운 스레드 생성

```java
public OrderResult placeOrder(OrderRequest request) {
    // 주문 생성 처리

    new Thread(() -> pushClient.sendPush(pushData)).start();

    // 푸시 발송을 기다리지 않고 반환
    return successResult();
}
```

요청마다 스레드를 만들면 생성 비용과 메모리 사용량이 크게 증가한다.

---

### 스레드 풀 사용

스레드 풀은 일정한 개수의 스레드를 미리 만들어 재사용한다.

```java
private final ExecutorService executor =
        Executors.newFixedThreadPool(50);

public OrderResult placeOrder(OrderRequest request) {
    // 주문 생성 처리

    executor.submit(() -> pushClient.sendPush(pushData));

    // 푸시 발송을 기다리지 않고 반환
    return successResult();
}
```

스레드 생성 비용과 메모리 사용량을 줄이고 동시 실행 수를 제한할 수 있다. 다만 스레드보다 작업이 많으면 나머지는 큐에서 대기하므로 풀과 큐의 크기를 적절히 설정해야 한다.

---

### Spring의 `@Async` 사용

Spring에서는 `@Async`로 특정 메서드를 별도 스레드에서 실행할 수 있다.

```java
@Service
public class PushService {

    @Async
    public void sendPushAsync(PushData pushData) {
        pushClient.sendPush(pushData);
    }
}
```

```java
public OrderResult placeOrder(OrderRequest request) {
    // 주문 생성 처리

    pushService.sendPushAsync(pushData);

    return successResult();
}
```

#### 비동기 메서드임을 이름에 드러내기

```java
pushService.sendPushAsync(pushData);
```

메서드 이름에 `Async`를 붙이면 비동기 실행 여부와 다른 예외 처리 방식을 호출부에서 알 수 있다.

---

### 호출한 곳에서 예외를 처리할 수 없다

비동기 메서드는 별도 스레드에서 실행되므로 호출한 곳의 `try-catch`로 내부 예외를 잡을 수 없다.

```java
public OrderResult placeOrder(OrderRequest request) {
    try {
        pushService.sendPushAsync(pushData);
    } catch (Exception exception) {
        // 비동기 작업에서 발생한 예외는 여기서 잡히지 않는다.
    }

    return successResult();
}
```

> 비동기 작업에서 발생한 예외는 비동기 메서드 내부에서 직접 처리해야 한다.

```java
@Async
public void sendPushAsync(PushData pushData) {
    try {
        pushClient.sendPush(pushData);
    } catch (Exception exception) {
        log.error("푸시 발송 실패", exception);

        // 실패 내역 저장 또는 재시도 처리
        recordPushFailure(pushData, exception);
    }
}
```

실패하면 로그나 실패 내역을 남기고 재시도하거나 수동으로 다시 처리할 수 있어야 한다.

---

### 비동기 실행과 트랜잭션

트랜잭션 안에서 호출한 비동기 메서드는 별도 스레드에서 실행되므로 기존 트랜잭션과 분리될 수 있다.

```java
@Transactional
public void placeOrder(OrderRequest request) {
    createOrder(request);

    // 별도 스레드에서 실행
    pushService.sendPushAsync(pushData);
}
```

`sendPushAsync()`에서 예외가 발생해도 호출 스레드로 전달되지 않아 주문 트랜잭션은 커밋될 수 있다. 하나의 트랜잭션으로 묶어야 하는 작업은 같은 스레드에서 실행하고, 비동기로 분리한다면 별도의 실패 처리와 재시도를 설계해야 한다.

---

### 스레드와 메모리

스레드는 각각 메모리를 사용한다. 스레드가 지나치게 많으면 메모리 사용량과 생성 비용, 스케줄링에 필요한 CPU 시간이 증가해 전체 성능이 떨어진다.

#### 스레드 풀의 한계

```text
작업 요청
   ↓
대기 큐
   ↓
스레드 풀
   ↓
외부 API 호출
```

외부 API가 느리면 스레드가 오래 반환되지 않고 대기 작업이 쌓인다. 스레드 풀을 사용하더라도 타임아웃, 큐 크기, 거부 정책을 고려해야 한다.

---

### 가상 스레드와 고루틴

외부 API나 DB 연동 같은 네트워크 I/O 작업에는 Java의 가상 스레드나 Go의 고루틴을 사용할 수 있다. 네이티브 스레드보다 적은 메모리를 사용해 많은 작업을 처리하는 데 유리하다.

---

### 핵심 정리

> 별도 스레드를 사용하면 외부 연동을 기다리지 않고 빠르게 응답할 수 있지만, 예외 처리와 트랜잭션이 자동으로 해결되지는 않는다.

- 비동기 작업 내부에서 오류를 처리한다.
- 기존 트랜잭션과 분리돼도 되는지 확인한다.
- 스레드와 대기 작업 수를 제한한다.

## 5.3 메시징

메시징 시스템은 데이터를 보내는 시스템과 처리하는 시스템 사이에서 메시지를 전달하고 보관한다.

![메시징 시스템을 이용한 비동기 연동](5장 사진/메시징 시스템을 이용한 비동기 연동 처리.png)

1. 시스템 A가 메시지를 생성한다.
2. 메시징 시스템에 전송한다.
3. 메시징 시스템이 메시지를 보관한다.
4. 시스템 B가 메시지를 받아 처리한다.

시스템 A는 시스템 B의 처리가 끝날 때까지 기다리지 않는다.

---

### 메시징 시스템을 사용하는 이유

#### 시스템 간 장애 격리

직접 연동하면 시스템 B의 지연이나 장애가 A까지 전파된다. 메시징 시스템은 메시지를 보관하는 버퍼 역할을 하므로 B는 자신의 처리량에 맞춰 처리할 수 있다. 단, 소비자가 계속 처리하지 못하면 메시지가 쌓여 생산자에게도 영향을 줄 수 있다.

### 소비자 확장이 쉽다

새로운 시스템 C가 같은 데이터를 사용해야 한다면 기존 메시지를 구독하도록 연결하면 된다.

![메시징 시스템을 이용한 소비자 확장](5장 사진/메시징 시스템을 이용하면 확장이 용이하다.png)

생산자는 소비자 수를 알 필요가 없어 시스템 간 결합도가 낮아진다.

---

### 생산자와 소비자

- **생산자(Producer)**: 메시지를 생성해 보내는 쪽
- **소비자(Consumer)**: 메시지를 받아 처리하는 쪽
- **게시자(Publisher)**: 메시지를 게시하는 쪽
- **구독자(Subscriber)**: 게시된 메시지를 구독하는 쪽

---

### 메시징 기술 비교

| 구분 | Kafka | RabbitMQ | Redis Pub/Sub |
|---|---|---|---|
| 주 용도 | 대규모 이벤트 스트림과 로그 처리 | 작업 큐와 복잡한 메시지 라우팅 | 실시간 알림과 단순 방송 |
| 메시지 저장 | 디스크에 일정 기간 보관 | 설정에 따라 영속화 가능 | 기본적으로 저장하지 않음 |
| 전달 방식 | 소비자가 읽는 Pull 방식 | 브로커가 전달하는 Push 방식 | 게시 즉시 구독자에게 전달 |
| 재처리 | 오프셋을 이용해 가능 | 재전달과 재처리 가능 | 불가능 |
| 순서 | 파티션 내부에서 보장 | 큐의 전달 순서를 유지하지만 병렬 처리 시 완료 순서는 달라질 수 있음 | 게시된 순서대로 전달 |
| 장점 | 높은 처리량, 수평 확장, 메시지 재처리 | ACK, 라우팅, 다양한 프로토콜과 패턴 지원 | 구조가 단순하고 지연 시간이 짧음 |
| 주의점 | 운영 복잡도가 높음 | 소비자가 느리면 큐에 메시지가 쌓임 | 구독자가 없거나 연결이 끊기면 메시지 유실 |

#### 선택 기준

- 대규모 이벤트 보관과 재처리가 필요하면 Kafka를 고려한다.
- 작업 큐와 복잡한 라우팅이 필요하면 RabbitMQ를 고려한다.
- 메시지 유실을 허용하고 단순한 실시간 전달이 필요하면 Redis Pub/Sub을 고려한다.

> 가장 유명한 기술보다 요구사항을 만족하면서 조직이 안정적으로 운영할 수 있는 기술을 선택해야 한다.

---

### 생산자가 고려할 사항

#### 메시지 전송 실패

메시지 전송 실패나 타임아웃이 발생하면 실패를 무시하거나 재시도하거나 실패 내역을 기록한다. 메시지 유실을 허용할 수 있는지에 따라 방법을 선택한다.

#### 재시도로 인한 중복 메시지

전송은 성공했지만 응답을 받지 못해 재시도하면 같은 메시지가 중복 전송될 수 있다. 메시지마다 고유 ID를 부여하고 재전송할 때도 같은 ID를 유지한다.

```json
{
  "messageId": "order-created-10001",
  "type": "ORDER_CREATED",
  "orderId": 10001
}
```

### DB 트랜잭션과 메시지 전송

#### 커밋 전에 메시지를 보내는 경우

![트랜잭션 롤백 전에 메시지를 전송하는 잘못된 구조](5장 사진/메시지를 전송한 뒤 DB 트랜잭션이 롤백되면 잘못된 메시지가 전송될 수 있다.png)

메시지를 보낸 뒤 DB 트랜잭션이 롤백되면 실제 주문은 실패했지만 주문 완료 메시지는 전달될 수 있다.

### 커밋 후 메시지를 보내는 경우

![DB 트랜잭션 완료 후 메시지를 전송하는 구조](5장 사진/트랜잭션이 완료 커밋 롤백된 뒤에 미시지를 전송한다.png)

커밋 후 전송하면 잘못된 메시지는 막을 수 있다. 하지만 커밋 직후 애플리케이션이 종료되면 DB에는 데이터가 반영되고 메시지는 전송되지 않을 수 있다.

---

### 글로벌 트랜잭션과 2PC

글로벌 트랜잭션은 DB 변경과 메시지 전송을 하나의 트랜잭션으로 묶지만 처리 속도가 느려지고 결합도가 높아진다.

> 글로벌 트랜잭션이 반드시 필요한 상황이 아니라면 DB와 메시징 시스템을 강하게 묶지 않는다.

---

### 소비자가 고려할 사항

#### 중복 메시지 처리

생산자의 재전송이나 소비자의 처리 실패로 같은 메시지를 여러 번 받을 수 있다. 처리한 메시지 ID를 기록해 이미 처리한 메시지를 무시한다.

```java
ConsumerRecords<String, String> records =
        consumer.poll(Duration.ofMillis(100));

for (ConsumerRecord<String, String> record : records) {
    Message message = messageConverter.convert(record.value());

    if (checkAlreadyHandled(message.getId())) {
        continue;
    }

    handle(message);
    recordHandledLog(message.getId());
}
```

#### 멱등성 확보

같은 메시지를 다시 처리해도 결과가 달라지지 않도록 멱등성을 확보해야 한다.

#### 처리 상태 모니터링

소비자의 처리 속도가 느리면 메시지가 계속 쌓인다. 대기 메시지 수, 소비 지연 시간, 처리 속도와 실패 횟수를 모니터링한다.

---

### 이벤트와 커맨드

| 이벤트 | 커맨드 |
|---|---|
| 주문이 생성됨 | 포인트 지급하기 |
| 로그인에 실패함 | 로그인 차단하기 |
| 상품 정보가 조회됨 | 배송 완료 문자 발송하기 |
| 배송이 완료됨 | 주문 상태 변경하기 |

#### 이벤트

이벤트는 이미 발생한 사실을 표현한다. 특정 소비자를 지정하지 않으며, 사건에 관심 있는 소비자가 각자 필요한 작업을 수행한다.

#### 커맨드

커맨드는 특정 소비자에게 작업 실행을 요청한다. 수행할 기능과 대상이 명확하다.

#### 차이 정리

| 구분 | 이벤트 | 커맨드 |
|---|---|---|
| 의미 | 발생한 사실 | 실행할 작업 |
| 표현 | 과거형 | 명령형 |
| 수신자 | 정해져 있지 않음 | 명확하게 정해짐 |
| 확장성 | 여러 소비자가 자유롭게 구독 | 특정 소비자가 처리 |
| 예시 | `OrderCreated` | `GivePoint` |

---

### 궁극적 일관성

비동기 메시징에서는 생산자의 변경이 소비자에게 즉시 반영되지 않아 일시적으로 데이터가 불일치할 수 있다. 메시지가 처리된 뒤 최종적으로 상태가 일치하는 특성을 궁극적 일관성이라고 한다.

---

### 핵심 정리

> 메시징 시스템은 생산자와 소비자를 분리해 장애 전파를 줄이고 확장을 쉽게 만들지만, 메시지 유실·중복·순서·트랜잭션·처리 지연을 직접 관리해야 한다.

---

## 5.3 트랜잭션 아웃박스 패턴

DB 커밋 후 메시지를 전송하더라도 애플리케이션이 중간에 종료되면 메시지가 유실될 수 있다.

```text
DB 커밋 성공
    ↓
애플리케이션 장애 발생
    ↓
메시지 전송 실패
```

> 업무 데이터와 전송할 메시지를 하나의 DB 트랜잭션으로 함께 저장한 뒤, 별도 중계기가 메시지를 전송한다.

---

### 동작 과정

1. 업무 데이터를 변경한다.
2. 메시지를 아웃박스 테이블에 저장한다.
3. 두 작업을 함께 커밋한다.
4. 중계기가 대기 메시지를 조회해 전송한다.
5. 전송 성공 시 완료 상태로 변경한다.

![트랜잭션 아웃박스 패턴의 동작 과정](5장 사진/트랜잭션 아웃박스 패턴의 동작 과정.png)

| 업무 데이터 변경 | 아웃박스 메시지 저장 | 결과 |
|---|---|---|
| 커밋 | 커밋 | 메시지 전송 대상이 됨 |
| 롤백 | 롤백 | 메시지가 전송되지 않음 |

업무 데이터와 메시지를 같은 트랜잭션에 저장하므로 커밋되지 않은 업무의 메시지는 전송되지 않는다.

---

### 메시지 중계기

```java
public void processMessages() {
    List<MessageData> waitingMessages = selectWaitingMessages();

    for (MessageData message : waitingMessages) {
        try {
            sendMessage(message);
            markDone(message.getId());
        } catch (Exception exception) {
            handleError(message, exception);
            break;
        }
    }
}
```

중계기는 `WAITING` 메시지를 순서대로 전송하고 성공하면 `DONE`, 반복 실패하면 `FAILED`로 변경한다.

---

### 메시지 순서

```text
1번 성공 → 2번 성공 → 3번 실패 → 처리 중단
```

순서가 중요하면 중간 메시지 실패 시 처리를 멈춘다. 실패 메시지가 이후 작업을 계속 막지 않도록 재시도 횟수와 실패 처리 기준도 정해야 한다.

---

### 전송 완료 기록 방법

#### 상태 칼럼 사용

```sql
SELECT *
FROM outbox
WHERE status = 'WAITING'
ORDER BY id ASC
LIMIT 100;
```

```sql
UPDATE outbox
SET status = 'DONE',
    processedAt = CURRENT_TIMESTAMP
WHERE id = ?;
```

상태 칼럼을 사용하면 대기·완료·실패 메시지를 쉽게 모니터링할 수 있다.

#### 마지막 처리 ID 기록

```sql
SELECT *
FROM outbox
WHERE id > :lastProcessedId
ORDER BY id ASC
LIMIT 100;
```

중계기가 마지막으로 전송한 메시지 ID를 저장하고 이후 메시지만 조회한다.

---

### 아웃박스 테이블 구조

| 칼럼 | 타입 | 설명 |
|---|---|---|
| `id` | `BIGINT` | 단순 증가 기본 키. 메시지 저장 순서를 판단하는 데 사용 |
| `messageId` | `VARCHAR` | 메시지 고유 ID. 중복 메시지 판별에 사용 |
| `messageType` | `VARCHAR` | 메시지 종류. 예: `LoginFailed`, `OrderPlaced` |
| `payload` | `CLOB` | 실제 메시지 데이터. 주로 JSON이나 XML 형식 사용 |
| `status` | `VARCHAR` | 처리 상태: `WAITING`, `DONE`, `FAILED` |
| `failCount` | `INT` | 메시지 전송 실패 횟수 |
| `occurredAt` | `TIMESTAMP` | 메시지가 발생한 시간 |
| `processedAt` | `TIMESTAMP` | 메시지 전송을 완료한 시간 |
| `failedAt` | `TIMESTAMP` | 마지막으로 전송에 실패한 시간 |

#### 메시지 상태

```text
WAITING  → 전송 대기
DONE     → 전송 완료
FAILED   → 반복 실패로 전송 중단
EXCLUDED → 운영자가 전송 대상에서 제외
```

한 번 실패했다고 바로 `FAILED`로 바꾸지 않고 일시적인 오류인지 확인할 수 있도록 재시도한다.

```text
1~4회 실패 → WAITING 상태로 재시도
5회 실패   → FAILED로 변경
FAILED 발생 → 모니터링 알림 전송
운영자 확인 → 재처리 또는 EXCLUDED 처리
```

---

### 중복 전송 가능성

```text
메시지 전송 성공
    ↓
DONE 상태로 변경하기 전에 중계기 종료
    ↓
다음 실행에서 같은 메시지 재전송
```

메시지 전송과 `DONE` 변경은 하나의 트랜잭션이 아니므로 중복 전송될 수 있다. 메시지 ID를 유지하고 소비자가 멱등하게 처리해야 한다.

> 아웃박스는 메시지 유실 가능성을 줄이지만, 중복 전송 가능성은 소비자가 처리해야 한다.

---

### 장점과 단점

#### 장점

- 업무 데이터와 메시지를 원자적으로 저장한다.
- DB 롤백 시 메시지도 함께 롤백된다.
- 메시징 시스템 장애에도 메시지가 DB에 남는다.

#### 단점

- 아웃박스 테이블과 중계기가 필요하다.
- 전송 지연과 중복 가능성이 남는다.
- 실패 메시지 모니터링과 운영 절차가 필요하다.

---

### 핵심 정리

> 트랜잭션 아웃박스 패턴은 업무 데이터와 메시지를 같은 DB 트랜잭션으로 저장해 메시지 유실과 잘못된 전송을 줄이는 패턴이다.

```text
업무 데이터 변경
    +
아웃박스 메시지 저장
    ↓
하나의 트랜잭션으로 커밋
    ↓
별도 중계기가 메시지 전송
    ↓
성공·실패 상태 기록
```

메시지 전송과 완료 처리는 원자적이지 않으므로 소비자의 멱등성 처리가 함께 필요하다.

---

## 5.4 배치 전송

배치 전송은 데이터를 모아 일정한 간격으로 전달하는 비동기 연동 방식이다.

- 결제 승인 데이터를 모아 다음 날 전송한다.
- 택배 발송 요청 데이터를 1시간 간격으로 전송한다.

### 기본 처리 과정

1. DB에서 전송할 데이터를 조회한다.
2. 조회한 데이터를 파일로 생성한다.
3. 파일을 연동 시스템에 전송한다.

파일 전송에는 FTP, SFTP, SCP 등을 사용한다.

### 파일 형식

| 형식 | 예시 | 특징 |
|---|---|---|
| 구분자 형식 | `값1^값2^값3` | 구조가 단순하고 파싱 속도가 빠름 |
| 이름-값 형식 | `이름1=값1^이름2=값2` | 값의 위치와 관계없이 의미를 알 수 있지만 데이터 크기가 커짐 |
| JSON 형식 | `{"id": 1, "name": "사용자"}` | 구현하기 쉽지만 부가 문자가 많아 데이터 크기가 커짐 |

#### 구분자 형식

```text
아이디^이름^이메일^전화번호
```

값의 위치에 따라 의미가 결정된다. 구조가 단순해 구현과 파싱이 빠르다.

#### 이름-값 형식

```text
id=1^name=홍길동^email=user@example.com
```

위치와 관계없이 값의 의미를 알 수 있지만 이름까지 포함해 크기가 커진다.

#### JSON 형식

```json
{"id": 1, "name": "홍길동", "email": "user@example.com"}
```

대부분의 언어가 변환 기능을 제공해 구현하기 쉽지만 부가 문자가 포함돼 크기가 커진다.

### 파일 연동 시 협의할 항목

- 송수신 주체
- 전송 시간
- 저장 경로와 파일 이름

#### 송수신 주체

생산자가 업로드할지 소비자가 다운로드할지 협의한다. 소비자 시스템을 외부에 노출하기 어려우면 소비자가 직접 다운로드할 수 있다.

#### 전송 시간

소비자가 데이터를 필요로 하는 시점보다 먼저 전송한다. 오류 대응 시간과 서로 다른 시간대도 고려한다.

#### 경로와 파일 이름

여러 서비스의 파일이 충돌하지 않도록 규칙을 정한다.

```text
/data/orders/order_20260810.txt
/data/payments/payment_20260810.txt
```

### 소비자의 파일 처리

1. 지정 경로에서 파일을 확인한다.
2. 파일을 읽어 시스템에 반영한다.
3. 파일이 없으면 정해진 후처리를 수행한다.
4. 완료된 파일은 다른 폴더로 이동한다.

```text
/input   → 처리 전 파일
/archive → 처리 완료 파일
```

완료 파일을 보관하면 중복 처리를 막고 필요할 때 재처리할 수 있다.

### 파일 이외의 배치 연동 방법

#### API를 이용한 일괄 전송

데이터 크기나 처리 항목이 적다면 API로 한꺼번에 전송해 파일 생성과 처리 과정을 줄일 수 있다.

#### 읽기 전용 DB 제공

같은 조직 안에서는 소비자에게 DB 읽기 권한을 제공해 필요한 데이터를 직접 조회하게 할 수 있다.

#### DB를 통한 직접 연동

레거시 시스템은 API나 파일 대신 DB 테이블로 연동하기도 한다. 이때 테이블 구조가 연동 명세 역할을 한다.

### 재처리 기능

파일 생성이나 네트워크 문제로 전송에 실패할 수 있으므로 자동 재시도와 수동 재처리 기능을 마련한다.

#### 자동 재시도

배치 완료 여부를 확인하고 실패하면 한두 번 다시 실행해 수동 처리를 줄인다.

#### 수동 재처리

자동 재시도 이후에도 실패할 수 있으므로 운영자가 직접 실행할 명령어나 API를 만든다.

```text
POST /admin/batches/{batchId}/retry
```

### 전송할 데이터가 없는 경우

데이터가 없더라도 빈 파일을 보낸다. 그래야 데이터가 없는 경우와 오류로 파일이 전송되지 않은 경우를 구분할 수 있다.

### 핵심 정리

- 파일 형식과 송수신 주체를 정한다.
- 전송 시간, 경로, 파일 이름을 합의한다.
- 완료 파일을 보관한다.
- 자동 재시도와 수동 재처리 방법을 마련한다.
- 데이터가 없어도 빈 파일을 전송한다.

---

## 5.5 CDC(Change Data Capture)

CDC는 변경된 데이터를 추적하고 식별해 해당 데이터로 작업을 수행할 수 있게 하는 소프트웨어 설계 패턴이다. DBMS가 제공하는 데이터 변경 통지 기능을 이용해 변경 데이터를 다른 시스템에 전달한다.

### CDC 처리 흐름

![CDC 패턴의 처리 흐름](5장 사진/CDC 패턴의 처리 흐름.png)

1. `INSERT`, `UPDATE`, `DELETE`로 DB 데이터가 변경된다.
2. DB가 변경 내용을 CDC 처리기에 전달한다.
3. CDC 처리기가 데이터를 확인하고 가공한다.
4. 변경 데이터를 대상 시스템에 전달한다.

DB는 커밋된 데이터만 변경 순서에 맞게 전달한다. 변경 데이터에는 작업 종류와 수정 전후 값이 포함된다.

### 변경 데이터 전달 방식

1. 변경 데이터를 그대로 전달한다.
2. 변경 데이터를 가공하거나 변환해 전달한다.

#### 변경 데이터를 그대로 전달

두 시스템의 데이터가 거의 일대일 관계라면 변경 데이터를 그대로 전달한다.

![변경 데이터를 그대로 대상 시스템에 전달하는 CDC 처리기](5장 사진/변경 데이터를 그대로 대상 시스템에 전파하는 CDC 처리기.png)

회원 시스템의 `member.name` 변경을 콘텐츠 시스템의 같은 칼럼에 반영하는 방식이다.

#### 변경 데이터를 변환해 전달

대상 시스템에 전체 데이터가 필요하지 않다면 필요한 값만 전달한다.

![변경 데이터를 변환해 전달하는 CDC 처리기](5장 사진/데이터를 변환해서 전판하는 CDC 처리기.png)

```text
주문 DB 변경
    ↓
CDC 처리기
    ↓
(주문 ID, 주문 상태)
    ↓
통지 시스템
```

### 변경 데이터 전달 대상

CDC 처리기는 목적에 따라 DB, 메시징 시스템, API로 데이터를 전달할 수 있다.

#### DB로 전달

두 시스템의 데이터 동기화가 목적이라면 DB 사이에서 데이터를 복제한다.

![DB 사이에서 데이터를 복제하는 CDC](5장 사진/단순히 DB 간에 데이터를 복제할 목적으로 사용하는 CDC.png)

```text
DB → 변경 내용 통지 → CDC 처리기 → 변경 내용 전달 → 대상 DB
```

#### 메시징 시스템으로 전달

메시징 시스템에 전달하면 여러 소비자가 같은 변경 데이터를 사용할 수 있다.

![메시징 시스템으로 변경 데이터를 전달하는 CDC](5장 사진/메시징 시스템에 변경 데이터를 전파하면 확장에 유리하다.png)

```text
DB
 ↓
CDC 처리기
 ↓
메시징 시스템
 ├─ 소비자 1
 └─ 소비자 2
```

### CDC와 이벤트의 차이

CDC는 데이터 변경 내용을 전달하지만 사건의 의미를 정확히 표현하지는 못한다.

```text
회원 암호를 초기화함
```

```text
회원 테이블의 암호 칼럼 변경
- 이전 암호
- 이후 암호
```

암호 칼럼의 변경만으로는 사용자가 변경했는지 시스템이 초기화했는지 알기 어렵다.

### CDC 처리 위치 기록

CDC 처리기는 변경 데이터를 어디까지 처리했는지 기록해야 한다. MySQL은 바이너리 로그의 위치 값을 이용하며, 재시작하면 저장한 위치부터 다시 읽는다.

```text
바이너리 로그 읽기
    ↓
변경 데이터 처리
    ↓
마지막 처리 위치 저장
```

위치를 기록하지 않으면 중단 중에 발생한 변경 데이터를 놓칠 수 있다.

### CDC가 유용한 경우

기존 시스템의 코드가 복잡하거나 일정이 부족해 연동 코드를 추가하기 어렵다면 CDC를 활용할 수 있다.

![신규 주문 시스템의 코드를 수정하지 않고 CDC로 데이터를 전달하는 구조](5장 사진/신주문 시스템의 코드를 수정하지 않고 CDC를 사용해서 변경 데이터를 관련 시스템에 전파했다.png)

신규 주문 시스템의 DB 변경을 CDC 처리기가 읽어 Kafka에 전달하고, 각 소비자가 필요한 데이터를 반영한다. 시스템 코드를 수정하지 않아 개발 일정에 주는 영향을 줄일 수 있다.

### 비동기 연동을 선택할 때

비동기 연동은 구조가 복잡해지고 시스템 사이의 데이터가 일시적으로 불일치할 수 있다. 반면 성능, 안정성, 자율성 측면에서 유리할 수 있다.

모든 연동을 비동기로 구현할 필요는 없다. 복잡도 증가보다 얻는 이점이 더 크다면 비동기 연동을 고려한다.
