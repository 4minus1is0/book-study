## 1. 🖥️ 개발자와 서버

규모가 큰 조직은 인프라·플랫폼 팀과 서비스 개발 팀이 분리되어 있다. 백엔드 개발자가 직접 OS를 설치하거나 관리할 기회가 적을 수 있지만, 서버 장애가 애플리케이션 문제인지 OS 문제인지 구분하려면 기본적인 서버 지식이 필요하다.

서버라는 용어는 문맥에 따라 다음 대상을 의미한다.

- 물리 장비 또는 가상 장비
- 장비에 설치된 운영체제
- 운영체제에서 실행되는 서버 프로그램

이 장에서는 서버 프로그램을 실행하는 리눅스 OS를 중심으로 계정, 프로세스, 디스크, 네트워크 등의 기초 관리 방법을 다룬다.

VirtualBox나 Vagrant 같은 가상화 도구를 사용하면 실제 장비를 다시 설치하지 않고도 OS 설치와 설정을 반복해서 연습할 수 있다.

> 🔑 **핵심:** 인프라 전문가 수준의 지식까지는 아니더라도, 백엔드 개발자는 서버 상태를 확인하고 기본적인 문제를 진단할 수 있어야 한다.

## 2. 👤 OS 계정과 권한

리눅스는 계정과 그룹을 기준으로 파일과 프로세스의 권한을 관리한다.

### root 계정

`root`는 모든 권한을 가진 관리자 계정이다. 대부분의 파일을 읽고 수정하거나 삭제할 수 있으므로 접근 인원을 제한해야 한다.

일반 사용자로 실행해야 하는 서버 프로그램을 `root`로 실행하면 다음과 같은 문제가 발생할 수 있다.

1. `root` 프로세스가 로그나 임시 파일을 생성한다.
2. 이후 일반 계정으로 프로세스를 재실행한다.
3. 일반 계정이 기존 파일을 수정하지 못한다.
4. 서버 프로그램이 시작 과정에서 비정상 종료된다.

서버 프로그램은 원칙적으로 해당 서비스를 위해 정한 일반 계정으로 실행한다.

### 파일 권한 확인

파일 권한은 `ls -l`로 확인한다.

```bash
ls -l
```

예시:

```text
-rwxr-xr-- 1 vagrant vagrant 28 Nov 10 08:26 run.sh
```

권한 문자열은 다음 구조다.

```text
- | rwx | r-x | r--
│    │     │     └─ 다른 사용자 권한
│    │     └─────── 그룹 권한
│    └───────────── 소유자 권한
└────────────────── 파일 종류
```

각 문자의 의미는 다음과 같다.

| 문자 | 권한 | 숫자 |
|---|---|---:|
| `r` | 읽기 | 4 |
| `w` | 쓰기 | 2 |
| `x` | 실행 | 1 |

### 숫자로 권한 변경

`chmod 754`는 소유자에게 모든 권한, 그룹에 읽기·실행 권한, 다른 사용자에게 읽기 권한을 부여한다.

```bash
chmod 754 run.sh
```

```text
소유자: 7 = 4 + 2 + 1 = rwx
그룹:   5 = 4 + 1     = r-x
기타:   4             = r--
```

### 기호로 권한 변경

소유자에게 실행 권한을 추가하려면 다음 명령을 사용한다.

```bash
chmod u+x run.sh
```

기호는 다음처럼 조합한다.

| 대상 | 의미 | 동작 | 의미 |
|---|---|---|---|
| `u` | 소유자 | `+` | 권한 추가 |
| `g` | 그룹 | `-` | 권한 제거 |
| `o` | 다른 사용자 | `=` | 지정한 권한으로 설정 |
| `a` | 모두 |  |  |

예시:

```bash
chmod g-x run.sh   # 그룹의 실행 권한 제거
chmod o=rx run.sh  # 다른 사용자에게 읽기·실행 권한 지정
chmod a+r run.sh   # 모든 사용자에게 읽기 권한 추가
```

> ⚠️ **주의:** `chmod 777`은 모든 사용자에게 읽기·쓰기·실행 권한을 부여한다. 편의를 위해 습관적으로 사용하면 안 된다.

파일을 삭제하기 전에는 현재 위치와 삭제 대상을 확인한다.

```bash
pwd
ls -la
```

특히 `root` 권한으로 삭제 명령을 실행하면 피해 범위가 커질 수 있다.

## 3. 🔐 `sudo`로 필요한 권한만 부여하기

개발자가 일반 계정을 사용하더라도 서비스 재시작처럼 관리자 권한이 필요한 작업이 있다. 매번 `root` 계정으로 로그인하는 대신 `sudo`로 필요한 명령만 다른 사용자 권한으로 실행할 수 있다.

`sudo` 정책은 주로 다음 위치에서 관리한다.

```text
/etc/sudoers
/etc/sudoers.d/
```

`sudoers` 파일은 문법 오류가 발생하지 않도록 `visudo`로 수정한다.

```bash
sudo visudo
```

기본 형식은 다음과 같다.

```text
사용자  호스트=(실행할 사용자)  허용할 명령
```

예를 들어 모든 명령을 허용하는 설정은 다음과 같다.

```text
user1 ALL=(ALL) ALL
```

하지만 이 설정은 사실상 광범위한 관리자 권한을 제공한다. 운영 서버에서는 필요한 명령만 허용한다.

```text
user1 ALL=(ALL) NOPASSWD: /usr/bin/systemctl start docker
user1 ALL=(ALL) NOPASSWD: /usr/bin/systemctl stop docker
```

`NOPASSWD`는 암호 입력 없이 명령을 실행하게 한다. `NOPASSWD: ALL`은 `root` 권한 전체를 넘겨주는 것과 비슷하므로 피한다.

> 🔑 **핵심:** `sudo`는 관리자 권한 전체를 공유하는 기능이 아니라 필요한 작업만 위임하는 수단으로 사용한다.

## 4. ⚙️ 프로세스 확인과 종료

클라이언트가 서버에 연결하지 못한다면 서버 프로세스가 실제로 실행 중인지 확인해야 한다. 이전 프로세스가 남았거나 시작 과정에서 오류가 발생했을 수 있다.

### 프로세스 목록 확인

```bash
ps aux
ps -eaf
```

주요 확인 항목은 다음과 같다.

- 프로세스 소유자
- 프로세스 ID(PID)
- CPU·메모리 사용량
- 실행 명령과 인자

메모리 사용량이 높은 프로세스 상위 항목은 다음처럼 확인할 수 있다.

```bash
ps aux --sort=-rss | head -n 6
```

CPU와 메모리 사용량을 실시간으로 확인할 때는 `top` 또는 `htop`을 사용한다.

```bash
top
htop
```

### 프로세스 종료

`kill`은 PID로 프로세스에 시그널을 보낸다.

```bash
kill -15 <PID>
kill -TERM <PID>
```

`SIGTERM`은 정상 종료를 요청한다. 프로세스는 임시 파일 삭제, 연결 정리, Spring 빈 종료 처리 같은 작업을 수행할 수 있다.

정상 종료 요청으로도 종료되지 않을 때만 `SIGKILL`을 검토한다.

```bash
kill -9 <PID>
kill -KILL <PID>
```

`SIGKILL`은 프로세스를 즉시 종료하므로 정리 작업을 수행할 기회를 주지 않는다.

> 🛑 **종료 순서:** 서비스의 정상 종료 명령 → `SIGTERM` → 충분한 대기와 재확인 → 마지막 수단으로 `SIGKILL`.

## 5. 🔄 포그라운드와 백그라운드 프로세스

포그라운드 프로세스는 터미널과 연결되어 키보드와 화면을 통해 사용자와 상호작용한다.

```bash
tail -f access.log
```

터미널 연결이 끊기면 해당 터미널에 연결된 프로세스도 종료될 수 있다.

### 백그라운드 실행

명령 뒤에 `&`를 붙이면 백그라운드로 실행된다.

```bash
java -Dserver.port=9090 -jar server.jar &
```

하지만 단순히 `&`만 붙인 프로세스는 로그아웃 시 HUP 시그널의 영향을 받을 수 있다.

터미널 연결이 끊겨도 계속 실행하려면 `nohup`을 함께 사용한다.

```bash
nohup java -Dserver.port=9090 -jar server.jar &
```

기본 출력은 `nohup.out`에 기록된다. 다른 로그 파일로 보내려면 리디렉션을 사용한다.

```bash
nohup java -Dserver.port=9090 -jar server.jar > server.log 2>&1 &
```

`2>&1`의 의미는 다음과 같다.

```text
2   : 표준 오류
>   : 리디렉션
&1  : 표준 출력이 향하는 대상
```

즉, 표준 오류를 표준 출력과 같은 파일에 기록한다.

> 상시 운영하는 서버 프로그램은 단순 `nohup`보다 프로세스 상태와 재시작 정책을 관리할 수 있는 서비스 관리 체계로 운영하는 것이 적절하다.

## 6. 💾 디스크 용량 관리

디스크 사용률이 100%에 도달하면 로그 기록, 임시 파일 생성, 프로세스 시작뿐 아니라 서버 접속까지 실패할 수 있다.

모니터링 도구에서 경고·위험 임계치를 설정하고, 사용률이 높아지면 원인을 즉시 확인해야 한다.

### 파일 시스템 사용률 확인

```bash
df -h
```

`-h`는 용량을 KB, MB, GB처럼 사람이 읽기 쉬운 단위로 표시한다.

### 디렉터리별 사용량 확인

현재 디렉터리의 파일과 하위 디렉터리 크기를 확인한다.

```bash
du -sh ./*
```

하위 디렉터리만 확인하려면 다음처럼 사용할 수 있다.

```bash
du -sh */
```

서버에서 디스크를 많이 사용하는 대표 항목은 다음과 같다.

- 로그 파일
- 업로드 과정에서 생성한 임시 파일
- 백업 파일
- 애플리케이션이 생성한 캐시나 작업 파일

### 오래된 파일 정리

30일보다 오래된 파일을 먼저 조회한다.

```bash
find /logs -mtime +29 -type f
```

대상이 정확한지 확인한 뒤 삭제한다.

```bash
find /logs -mtime +29 -type f -delete
```

`-delete`는 복구하기 어려운 삭제 작업이다. 실행 위치, 대상 경로, 검색 결과를 먼저 확인해야 한다.

### 로그 관리

로그 파일은 다음 정책으로 관리한다.

- 일정 기간이 지난 로그 삭제
- 장기 보관 로그를 NAS나 객체 스토리지로 이동
- 오래된 텍스트 로그 압축
- 날짜·크기 기준 로그 로테이션
- 임시 파일 정리 주기 설정

한 디렉터리에 파일이 지나치게 많아지면 탐색 성능이 저하될 수 있다. 날짜나 시간, 해시 값을 기준으로 하위 디렉터리를 나눠 저장한다.

디스크가 임계 상태이고 서비스를 즉시 중단할 수 없다면 로그 파일을 비우는 방법을 고려할 수 있다.

```bash
cp /dev/null out.log
```

이 명령은 기존 로그 내용을 모두 잃게 만든다. 정상적인 로그 관리 방법이 아니라 긴급 공간 확보를 위한 마지막 수단이다.

> 🔑 **핵심:** 디스크가 가득 찬 뒤 파일을 찾는 것이 아니라 사용률 알림, 보관 기간, 로그 로테이션을 미리 구성한다.

## 7. 📂 파일 디스크립터 제한

프로세스가 파일이나 네트워크 소켓을 열면 OS로부터 파일 디스크립터(File Descriptor, FD)를 할당받는다.

프로세스가 제한보다 많은 파일이나 소켓을 열면 다음 오류가 발생할 수 있다.

```text
Too many open files
```

트래픽이 증가하면 동시 소켓 수도 증가하므로 파일 디스크립터 제한을 미리 확인해야 한다.

### 현재 세션의 제한 확인

```bash
ulimit -a
ulimit -n
```

현재 셸 세션에서 제한을 변경할 수 있다.

```bash
ulimit -n 100000
```

이 변경은 현재 세션에만 적용되고 로그아웃하면 사라진다. 또한 hard limit보다 큰 값은 일반 사용자가 지정할 수 없다.

### 사용자 기본 제한

사용자의 기본 제한은 `/etc/security/limits.conf`에서 설정할 수 있다.

```text
* soft nofile 100000
* hard nofile 100000
```

- `soft`: 프로세스에 기본 적용되는 값
- `hard`: 사용자가 올릴 수 있는 최대 값

### systemd 서비스 제한

systemd로 실행되는 서비스는 일반 로그인 셸의 `ulimit` 설정과 별도로 관리된다.

기본값 확인:

```bash
systemctl show -p DefaultLimitNOFILE
```

systemd 전체 기본값은 `/etc/systemd/system.conf`에서 설정한다.

```text
DefaultLimitNOFILE=1048576
```

개별 서비스는 유닛 파일에 설정한다.

```ini
[Service]
LimitNOFILE=1048576
```

설정 변경 후 systemd 설정을 다시 읽는다.

```bash
sudo systemctl daemon-reload
```

### 커널 수준 제한

한 프로세스가 설정할 수 있는 최대 파일 디스크립터 수를 확인한다.

```bash
sysctl fs.nr_open
```

시스템 전체 파일 디스크립터 한도를 확인한다.

```bash
sysctl fs.file-max
```

`/etc/sysctl.conf`를 변경했다면 다음 명령으로 반영한다.

```bash
sudo sysctl -p
```

### 실행 중인 프로세스 확인

프로세스에 적용된 제한을 확인한다.

```bash
cat /proc/<PID>/limits
prlimit --pid <PID>
```

프로세스가 현재 사용 중인 파일 디스크립터를 확인한다.

```bash
lsof -p <PID>
lsof -p <PID> | wc -l
```

파일 디스크립터 제한은 다음 계층을 구분해서 확인한다.

| 계층 | 확인 대상 |
|---|---|
| 셸 세션 | `ulimit` |
| 사용자 기본값 | `limits.conf` |
| systemd 서비스 | `DefaultLimitNOFILE`, `LimitNOFILE` |
| 프로세스 실제 값 | `/proc/<PID>/limits` |
| 커널 최대값 | `fs.nr_open`, `fs.file-max` |

## 8. 🕒 서버 시간 동기화

컴퓨터의 시계는 실제 시간과 조금씩 차이가 생긴다. 서버가 여러 대라면 각 서버의 오차도 달라진다.

시간 차이는 다음 문제를 일으킬 수 있다.

- 분산 시스템에서 최신 데이터 판단 오류
- 로그 순서 왜곡
- 만료 시간과 스케줄 계산 오류
- 제한 시간 안에 처리해야 하는 외부 API 요청 실패

실제 사례처럼 서버 시간이 30초 이상 어긋나면 생성 후 15초 안에 도착해야 하는 결제 요청이 간헐적으로 거절될 수 있다.

`chrony`나 NTP 서비스를 이용해 서버 시간을 주기적으로 동기화한다. 최초 서버 구성 체크리스트에 시간 동기화 설정을 포함하는 것이 좋다.

> 시간은 단순 표시 정보가 아니라 분산 시스템의 데이터 순서와 요청 유효성을 결정하는 운영 자원이다.

## 9. 📅 크론으로 작업 스케줄링

크론(cron)은 유닉스 계열 OS의 시간 기반 스케줄러다. 계정별 크론탭에 실행 시각과 명령을 등록한다.

사용 예시는 다음과 같다.

- 오래된 로그 삭제
- 로그 압축
- DB 백업
- 백업 파일 업로드

### 크론탭 조회와 편집

```bash
crontab -l
crontab -e
```

크론 표현식은 다섯 개의 시간 필드와 실행 명령으로 구성된다.

```text
┌──────── 분         0~59
│ ┌────── 시         0~23
│ │ ┌──── 월의 일    1~31
│ │ │ ┌── 월         1~12
│ │ │ │ ┌ 요일       0~6, 0은 일요일
│ │ │ │ │
* * * * * 실행할 명령
```

예시:

```cron
0 0 * * *      # 매일 00:00
30 1 1 * *     # 매월 1일 01:30
5 4 * * 0      # 매주 일요일 04:05
0 1,2,3 * * *  # 매일 01:00, 02:00, 03:00
0,30 5 * * *   # 매일 05:00, 05:30
*/10 1 * * *   # 매일 01시 동안 10분 간격
0 */2 * * *    # 2시간 간격으로 정각에 실행
```

실행 결과를 로그로 남기려면 리디렉션을 사용한다.

```cron
0 4 * * * /data/project/run.sh > /data/project/out.log 2>&1
```

계정이 크론을 사용할 수 없다면 `cron.deny` 또는 `cron.allow` 정책을 확인한다. 일회성 작업을 예약할 때는 `at` 명령을 사용할 수 있다.

> 🔑 **핵심:** 스케줄 등록만으로 끝내지 말고 실행 결과와 실패 원인을 확인할 로그를 남긴다.

## 10. ⌨️ `alias`로 반복 명령 줄이기

`alias`는 자주 사용하는 긴 명령에 짧은 별칭을 부여한다.

```bash
alias cdweb='cd /var/www/html'
cdweb
pwd
```

터미널에서 직접 등록한 별칭은 현재 세션에만 적용된다. 매번 자동으로 적용하려면 `~/.bashrc`에 등록한다.

```bash
alias cdweb='cd /var/www/html'
```

등록된 전체 별칭은 다음 명령으로 확인한다.

```bash
alias
```

`~/.bash_profile`과 `~/.bashrc`의 차이는 다음과 같다.

| 파일 | 실행 시점 | 주요 용도 |
|---|---|---|
| `.bash_profile` | 로그인할 때 | `PATH` 같은 전체 세션 환경 변수 |
| `.bashrc` | 새로운 Bash 셸을 시작할 때 | 별칭과 셸별 설정 |

일반적으로 `.bash_profile`에서 `.bashrc`를 불러오도록 구성한다.

## 11. 🌐 네트워크 정보와 연결 상태 확인

외부 연동이 실패할 때는 다음을 구분해서 확인한다.

```text
서버 IP가 올바른가?
→ 목적지 포트까지 연결되는가?
→ 서버 프로세스가 실제 포트를 열고 있는가?
→ API가 정상 응답하는가?
```

### IP 정보 확인

책에서는 `ifconfig`로 네트워크 인터페이스 정보를 확인한다.

```bash
ifconfig
```

주요 확인 항목은 다음과 같다.

- IPv4 주소: `inet`
- IPv6 주소: `inet6`
- MAC 주소: `ether`
- 수신·송신 데이터: `RX`, `TX`
- 로컬 루프백 인터페이스: `lo`

### 특정 포트 연결 확인

TCP 443 포트 연결을 확인한다.

```bash
nc -z -v www.daum.net 443
```

- `-z`: 데이터를 보내지 않고 포트 연결만 확인
- `-v`: 상세 정보 출력

UDP 포트는 `-u` 옵션을 추가한다.

```bash
nc -z -u -v localhost 6100
```

`nc`를 임시 서버처럼 실행해 두 노드 간 연결을 확인할 수도 있다.

```bash
nc -l -v -p 1234
```

옵션 표기는 `nc` 구현체에 따라 다를 수 있다.

### API 응답 확인

HTTP API 호출 결과는 `curl` 또는 `wget`으로 확인할 수 있다.

```bash
curl https://example.com/api/health
wget https://example.com/file
```

### 서버가 열어 둔 포트 확인

책에서는 `netstat`으로 리스닝 소켓과 사용 프로세스를 확인한다.

```bash
netstat -lputn
```

| 옵션 | 의미 |
|---|---|
| `-l` | 리스닝 소켓 |
| `-p` | PID와 프로그램 이름 |
| `-u` | UDP 소켓 |
| `-t` | TCP 소켓 |
| `-n` | 주소와 포트를 숫자로 표시 |

특정 포트가 사용 중인지 검색한다.

```bash
netstat -anp | grep 12931
```

서버 프로그램이 `Address already in use` 오류로 시작하지 못한다면 동일 포트를 사용하는 기존 프로세스가 있는지 확인한다.

> ℹ️ 배포판에 따라 `ifconfig`와 `netstat`이 기본 설치되어 있지 않을 수 있다. 이 장에서는 책에 나온 명령을 기준으로 정리한다.

## 12. 🧰 중요 명령어 모음

### 계정과 파일 권한

| 명령어 | 용도 | 주의 사항 |
|---|---|---|
| `pwd` | 현재 디렉터리 확인 | 삭제 작업 전 반드시 확인 |
| `ls -la` | 파일 목록과 권한 확인 | 숨김 파일 포함 |
| `chmod 754 run.sh` | 숫자로 권한 설정 | 필요한 권한만 부여 |
| `chmod u+x run.sh` | 소유자 실행 권한 추가 | `777` 습관적 사용 금지 |
| `sudo visudo` | `sudoers` 안전하게 편집 | 문법 오류 방지 |

### 프로세스

| 명령어 | 용도 | 주의 사항 |
|---|---|---|
| `ps aux` | 실행 중인 프로세스 확인 | 소유자, PID, 자원 사용량 확인 |
| `ps -eaf` | 전체 프로세스와 실행 인자 확인 | 프로세스 검색에 활용 |
| `top` | CPU·메모리 실시간 확인 | 종료는 `q` |
| `htop` | 프로세스 상태를 대화형으로 확인 | 별도 설치가 필요할 수 있음 |
| `ps aux --sort=-rss \| head -n 6` | 메모리 사용량 상위 프로세스 확인 | 헤더 포함 6줄 출력 |
| `kill -15 <PID>` | 정상 종료 요청 | 우선 사용 |
| `kill -9 <PID>` | 프로세스 강제 종료 | 마지막 수단 |

### 백그라운드 실행과 로그

| 명령어 | 용도 | 주의 사항 |
|---|---|---|
| `tail -f access.log` | 로그 변경 내용 실시간 확인 | 종료는 `Ctrl+C` |
| `명령어 &` | 백그라운드 실행 | 로그아웃 시 종료될 수 있음 |
| `nohup 명령어 &` | 터미널 종료 후에도 실행 | 기본 출력은 `nohup.out` |
| `nohup 명령어 > app.log 2>&1 &` | 출력과 오류를 같은 로그에 기록 | 로그 로테이션 필요 |

### 디스크

| 명령어 | 용도 | 주의 사항 |
|---|---|---|
| `df -h` | 파일 시스템 사용률 확인 | 사용률과 마운트 지점 확인 |
| `du -sh ./*` | 현재 위치의 항목별 용량 확인 | 큰 디렉터리 탐색 |
| `find /logs -mtime +29 -type f` | 오래된 파일 조회 | 삭제 전 결과 확인 |
| `find /logs -mtime +29 -type f -delete` | 오래된 파일 삭제 | 복구하기 어려움 |
| `cp /dev/null out.log` | 로그 파일 비우기 | 내용 전체 유실, 긴급 상황 전용 |

### 파일 디스크립터

| 명령어 | 용도 |
|---|---|
| `ulimit -a` | 현재 세션의 전체 제한 확인 |
| `ulimit -n` | 열린 파일 수 제한 확인 |
| `systemctl show -p DefaultLimitNOFILE` | systemd 기본 FD 제한 확인 |
| `sysctl fs.nr_open` | 프로세스별 최대 FD 제한 확인 |
| `sysctl fs.file-max` | 시스템 전체 FD 제한 확인 |
| `cat /proc/<PID>/limits` | 실행 중인 프로세스 제한 확인 |
| `prlimit --pid <PID>` | 프로세스 자원 제한 확인 |
| `lsof -p <PID>` | 프로세스가 연 파일과 소켓 확인 |
| `lsof -p <PID> \| wc -l` | 사용 중인 FD 개수 추정 |

### 크론과 별칭

| 명령어 | 용도 |
|---|---|
| `crontab -l` | 현재 계정의 크론 작업 조회 |
| `crontab -e` | 현재 계정의 크론 작업 편집 |
| `alias cdweb='cd /var/www/html'` | 현재 세션에 별칭 등록 |
| `alias` | 등록된 전체 별칭 확인 |

### 네트워크

| 명령어 | 용도 |
|---|---|
| `ifconfig` | 네트워크 인터페이스와 IP 확인 |
| `nc -z -v <HOST> <PORT>` | TCP 포트 연결 확인 |
| `nc -z -u -v <HOST> <PORT>` | UDP 포트 연결 확인 |
| `nc -l -v -p <PORT>` | 임시 리스닝 서버 실행 |
| `curl <URL>` | HTTP API 요청과 응답 확인 |
| `wget <URL>` | URL의 파일이나 응답 내려받기 |
| `netstat -lputn` | 리스닝 TCP·UDP 포트 확인 |
| `netstat -anp \| grep <PORT>` | 특정 포트를 사용하는 연결·프로세스 검색 |

## ✅ 정리

백엔드 개발자가 서버 문제를 진단하려면 애플리케이션 외부의 상태도 확인할 수 있어야 한다.

주요 원칙은 다음과 같다.

- 서버 프로그램은 목적에 맞는 일반 계정으로 실행한다.
- `root`, `sudo`, 파일 권한은 최소 권한 원칙에 따라 관리한다.
- 연결 장애가 발생하면 프로세스와 리스닝 포트를 함께 확인한다.
- 프로세스는 정상 종료를 먼저 시도하고 강제 종료는 마지막에 사용한다.
- 상시 실행 프로그램은 터미널 연결과 분리해서 관리한다.
- 디스크 사용률, 로그 보관 기간, 임시 파일 정리 정책을 설정한다.
- 트래픽 증가 전에 파일 디스크립터 제한을 확인한다.
- 분산 시스템과 외부 연동을 위해 서버 시간을 동기화한다.
- 크론 작업은 실행 결과와 실패 로그를 남긴다.
- 네트워크 문제는 IP, 포트 연결, 리스닝 소켓, API 응답 순서로 좁혀간다.

> 🧭 **핵심 원칙:** 서버 장애를 애플리케이션 문제로 단정하지 말고 계정·프로세스·디스크·파일 디스크립터·시간·네트워크 계층을 순서대로 확인한다.
