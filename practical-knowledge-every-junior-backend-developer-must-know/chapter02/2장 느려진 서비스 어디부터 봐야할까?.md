## 1. 처리량과 응답 시간

### 1.1 응답 시간이란?

**응답 시간(Response Time)**은 사용자의 요청을 처리하고 응답하기까지 걸리는 시간이다.

응답 시간은 다음 세 구간으로 나눌 수 있다.

1. API 요청 전송 시간
2. 서버 처리 시간
3. API 응답 전송 시간

<img width="321" height="197" alt="응답 시간 구성" src="https://github.com/user-attachments/assets/c8b00dfe-02db-474e-b1ad-081a553efc45" />

일반적으로 서버 처리 시간에서는 다음 작업이 큰 비중을 차지한다.

- DB 연동
- 외부 API 연동

### 1.2 처리량이란?

**처리량(Throughput)**은 단위 시간 동안 시스템이 처리하는 작업량이다.

처리량은 다음 단위로 표현한다.

- **TPS(Transaction Per Second)**: 초당 처리한 트랜잭션 수
- **RPS(Request Per Second)**: 초당 처리한 요청 수

<img width="395" height="139" alt="처리량과 응답 시간 관계" src="https://github.com/user-attachments/assets/738e86fc-f22e-4a41-9078-c592c16c67ad" />

유입되는 요청이 시스템의 최대 TPS를 초과하면 처리되지 못한 요청이 쌓인다.  
대기 시간이 증가하면서 전체 응답 시간도 느려진다.

이를 개선하는 방법은 크게 두 가지다.

- 서버가 동시에 처리할 수 있는 요청 수를 늘린다.
- 개별 요청의 처리 시간을 줄여 전체 대기 시간을 줄인다.

### 1.3 성능 개선의 출발점

성능 개선을 시작하기 전에 다음 목표를 정해야 한다.

- 목표 TPS 또는 RPS
- 목표 평균 응답 시간
- 허용 가능한 최대 응답 시간
- 허용 가능한 오류율

목표 없이 성능을 개선하면 개선 여부를 객관적으로 판단하기 어렵다.

> **핵심:** 감으로 병목을 추측하지 말고, 목표를 정한 뒤 측정 결과를 바탕으로 개선한다.

## 2. 서버 성능 개선 기초

다음과 같은 현상이 발생한다면 서버에 성능 문제가 있을 가능성이 크다.

> - 순간적으로 모든 사용자 요청의 응답 시간이 심각하게 느려진다.
> - 10초 이상 걸리는 요청이 늘어난다.
> - 다수의 요청에서 연결 시간 초과 오류가 발생한다.
> - 서버를 재시작하면 잠시 정상화되지만 다시 느려진다.
> - 트래픽이 줄어들 때까지 문제가 계속된다.

성능 문제의 원인을 감으로 추측할 수는 있지만, 정확한 원인을 찾으려면 반드시 성능을 측정해야 한다.

일반적으로 병목은 다음 구간에서 자주 발생한다.

- DB 연동
- 외부 API 연동
- 서버의 CPU 또는 메모리
- 네트워크
- 동시 요청 처리 구간

DB와 외부 API 연동 문제는 각각 3장과 4장에서 다루고, 이 장에서는 서버 관점의 개선 방법을 살펴본다.

---

## 3. 병목 지점과 확장

### 3.1 수직 확장

**수직 확장(Scale Up)**은 기존 서버의 자원을 증가시키는 방법이다.

예시:

- CPU 코어 증가
- 메모리 증설
- 디스크 성능 향상
- 네트워크 대역폭 증가

장점:

- 구조 변경이 적다.
- 비교적 빠르게 적용할 수 있다.

제약:

- 높은 사양일수록 비용이 증가한다.
- 한 대의 서버가 가질 수 있는 자원에는 한계가 있다.
- 단일 서버 장애에 취약할 수 있다.

### 3.2 수평 확장

**수평 확장(Scale Out)**은 서버를 추가해 여러 서버가 요청을 나누어 처리하도록 하는 방법이다.

장점:

- 전체 처리량을 높일 수 있다.
- 일부 서버에 장애가 발생해도 다른 서버가 요청을 처리할 수 있다.

제약:

- 로드 밸런싱이 필요하다.
- 세션과 캐시 등의 상태 관리가 복잡해진다.
- 서버 간 트래픽 분배가 적절하지 않으면 효과가 제한된다.

> 수평 확장은 처리량을 높일 수 있지만, 개별 요청의 실행 시간을 획기적으로 줄이지는 못한다.

---

## 4. DB 커넥션 풀

### 4.1 커넥션 풀이 필요한 이유

서버가 DB를 사용하려면 일반적으로 다음 과정을 거친다.

1. DB 연결
2. 쿼리 실행
3. DB 연결 종료

매 요청마다 DB 연결을 생성하고 종료하면 연결 과정 자체가 응답 시간에 영향을 준다.

**DB 커넥션 풀(Connection Pool)**은 DB에 연결된 커넥션을 미리 생성해 보관한다.  
요청이 들어오면 새로운 연결을 만들지 않고 풀에 있는 커넥션을 빌려 사용한 뒤 반납한다.

### 4.2 커넥션 풀 크기

커넥션 풀 크기는 풀에 유지할 커넥션의 수를 결정하는 설정이다.

커넥션 풀 크기가 너무 작으면 다음 문제가 발생한다.

- 사용 가능한 커넥션을 기다리는 시간이 길어진다.
- 요청 처리량이 감소한다.

반대로 너무 크면 다음 문제가 발생한다.

- DB의 CPU 사용률이 증가한다.
- DB가 동시에 처리해야 하는 쿼리가 많아진다.
- 컨텍스트 스위칭과 경합이 증가할 수 있다.
- 결과적으로 DB 부하가 커질 수 있다.

따라서 커넥션 풀 크기는 다음 요소를 측정해 결정해야 한다.

- 요청량
- 쿼리 실행 시간
- DB가 처리할 수 있는 동시 연결 수
- 서버 인스턴스 수
- 커넥션 대기 시간

> 커넥션 수를 무조건 늘린다고 성능이 향상되는 것은 아니다.

### 4.3 커넥션 대기 시간

커넥션 대기 시간은 커넥션 풀에서 사용 가능한 커넥션을 얻기 위해 기다릴 수 있는 최대 시간이다.

HikariCP의 기본 대기 시간은 30초다.  
일반적인 서비스에서는 30초가 지나치게 길 수 있으므로 서비스 특성에 따라 약 **0.5초에서 3초 이내**로 설정할 수 있다.

대기 시간을 짧게 설정하면 다음 효과가 있다.

- 사용자가 오랫동안 응답을 기다리지 않게 할 수 있다.
- 빠르게 실패시킨 뒤 사용자 친화적인 오류 메시지를 보여줄 수 있다.
- 서버에서 동시에 처리 중인 요청 수를 제한할 수 있다.
- 서버 부하가 일정 수준을 넘지 않도록 방어할 수 있다.

단, 적절한 값은 서비스의 목표 응답 시간과 트래픽 특성을 측정해 결정해야 한다.

### 4.4 최대 유휴 시간

**최대 유휴 시간(Maximum Idle Time)**은 사용되지 않는 커넥션을 풀에 유지하는 최대 시간이다.

DB나 네트워크 장비는 일정 시간 동안 통신이 없는 연결을 종료할 수 있다.  
서버의 최대 유휴 시간을 이보다 짧게 설정하면 외부에서 연결을 끊기 전에 커넥션 풀에서 커넥션을 정리할 수 있다.

### 4.5 유효성 검사

유효성 검사는 커넥션이 실제로 사용 가능한 상태인지 확인하는 과정이다.

일반적으로 다음 방법을 사용한다.

- JDBC 드라이버의 유효성 검사 기능 사용
- 간단한 `SELECT` 쿼리 실행

유효하지 않은 커넥션을 요청 처리에 사용하면 오류가 발생할 수 있으므로, 풀에서 빌려주기 전에 커넥션 상태를 적절히 확인해야 한다.

### 4.6 최대 유지 시간

**최대 유지 시간(Maximum Lifetime)**은 커넥션이 생성된 후 풀에 유지될 수 있는 최대 시간이다.

최대 유지 시간이 지나면 커넥션이 유효하더라도 닫고 풀에서 제거한다. 이후 새로운 커넥션을 생성한다.

설정 목적은 다음과 같다.

- DB나 네트워크 장비가 커넥션을 강제로 끊기 전에 교체한다.
- 오래된 커넥션을 주기적으로 정리한다.
- 이미 끊어진 커넥션이 풀에 남는 문제를 줄인다.

DB나 네트워크의 연결 제한 시간보다 커넥션 풀의 최대 유지 시간을 짧게 설정하는 것이 일반적이다.

## 5. 서버 캐시

### 5.1 캐시가 필요한 이유

수평 확장은 전체 처리량을 늘릴 수 있지만, 개별 요청의 실행 시간을 직접 줄이지는 못한다.

반복적으로 조회되는 데이터를 캐시에 저장하면 DB 대신 캐시에서 값을 읽을 수 있다.

<img width="395" height="321" alt="서버 캐시 구조" src="https://github.com/user-attachments/assets/80c84ab9-b28f-4998-8645-21e25891062a" />

캐시는 일반적으로 키와 값의 형태로 데이터를 저장한다.

```text
Key   → Value
user:1 → 사용자 정보
post:10 → 게시글 정보
```

캐시를 사용하면 다음 효과를 얻을 수 있다.

- DB 조회 횟수 감소
- 응답 시간 단축
- DB 부하 감소
- 반복 계산 감소

### 5.2 캐시 적중률

**캐시 적중률(Cache Hit Rate)**은 전체 캐시 조회 중 실제로 캐시에서 데이터를 찾은 비율이다.

```text
캐시 적중률 = 캐시 적중 횟수 / 전체 캐시 조회 횟수
```

캐시 적중률이 높을수록 DB나 외부 시스템에 대한 요청을 더 많이 줄일 수 있다.

### 5.3 캐시 삭제 규칙

캐시는 메모리를 사용하므로 저장할 수 있는 데이터의 양에 한계가 있다.  
캐시 공간이 부족하면 새로운 데이터를 저장하기 위해 기존 데이터를 삭제해야 한다.

대표적인 삭제 규칙은 다음과 같다.

- **LRU(Least Recently Used)**: 가장 오래 사용되지 않은 데이터 삭제
- **LFU(Least Frequently Used)**: 사용 빈도가 가장 낮은 데이터 삭제
- **FIFO(First In First Out)**: 가장 먼저 저장된 데이터 삭제

캐시 데이터의 접근 특성에 따라 적절한 삭제 규칙을 선택해야 한다.

### 5.4 로컬 캐시와 리모트 캐시

<img width="558" height="207" alt="로컬 캐시와 리모트 캐시" src="https://github.com/user-attachments/assets/4cc37549-5185-41b0-aa74-f3d8f01f5b1f" />

#### 로컬 캐시

서버 프로세스의 메모리에 데이터를 저장한다.

장점:

- 네트워크 통신이 없어 속도가 매우 빠르다.
- 별도의 캐시 서버가 필요하지 않다.

제약:

- 저장할 수 있는 크기가 서버 메모리에 제한된다.
- 서버마다 서로 다른 캐시 데이터를 가질 수 있다.
- 서버 프로세스를 재시작하면 캐시가 초기화된다.
- 배포가 잦으면 캐시 적중률이 반복적으로 낮아질 수 있다.

#### 리모트 캐시

Redis와 같은 별도 캐시 서버에 데이터를 저장한다.

장점:

- 여러 서버가 동일한 캐시 데이터를 공유할 수 있다.
- 저장 공간을 비교적 유연하게 확장할 수 있다.
- 애플리케이션 서버가 재시작되어도 캐시를 유지할 수 있다.

제약:

- 네트워크 통신이 필요하므로 로컬 캐시보다 느리다.
- 별도의 캐시 서버를 운영해야 한다.
- 시스템 구조와 장애 대응이 복잡해진다.

### 5.5 캐시 사전 적재

서버 재시작이나 배포 직후에는 캐시가 비어 있어 캐시 적중률이 순간적으로 0에 가까워질 수 있다.  
이 상태에서 요청이 몰리면 모든 요청이 DB로 전달되어 부하가 급격히 증가할 수 있다.

이를 방지하기 위해 자주 사용되는 데이터를 미리 캐시에 적재할 수 있다.

이를 **캐시 워밍(Cache Warming)** 또는 **캐시 사전 적재**라고 한다.

### 5.6 캐시 무효화

**캐시 무효화(Cache Invalidation)**는 더 이상 유효하지 않은 데이터를 적절한 시점에 캐시에서 제거하는 작업이다.

예를 들어 게시글 내용이 변경되었다면 기존 게시글 캐시도 즉시 삭제하거나 갱신해야 한다.

캐시 무효화 전략은 데이터 특성에 따라 달라진다.

- 변경이 드문 데이터: 긴 만료 시간 적용
- 변경이 잦은 데이터: 짧은 만료 시간 적용
- 변경 사항이 즉시 반영되어야 하는 데이터: 변경 시 즉시 무효화
- 여러 서버가 공유해야 하는 데이터: 리모트 캐시 사용

로컬 캐시는 특정 서버 프로세스 안에서만 변경된다.  
여러 서버에서 데이터의 일관성을 유지해야 하거나 변경에 민감한 정보는 리모트 캐시가 더 적합하다.

## 6. 가비지 컬렉터와 메모리 사용

Java, Go, Python 등의 언어는 더 이상 사용하지 않는 메모리를 정리하기 위해 가비지 컬렉터를 사용한다.

일부 GC 단계에서는 애플리케이션 실행이 일시적으로 중단되는 **Stop-The-World**가 발생한다.  
이 중단 시간은 서버의 응답 시간에 영향을 줄 수 있다.

일반적으로 다음 조건에서 GC 부담이 커질 수 있다.

- 힙 크기가 큰 경우
- 생성되는 객체 수가 많은 경우
- 수명이 긴 객체가 많은 경우
- 대량 데이터를 한 번에 메모리에 올리는 경우

힙 크기를 줄이면 한 번의 GC 시간이 줄어들 수 있지만, 다음 제약이 발생한다.

- GC가 더 자주 실행될 수 있다.
- 한 번에 많은 데이터를 처리하기 어렵다.
- 메모리가 부족하면 `OutOfMemoryError`가 발생할 수 있다.

따라서 힙 크기만 조정하기보다 불필요한 객체 생성과 대량 메모리 할당을 먼저 줄여야 한다.

### 6.1 파일 전체를 메모리에 올리는 코드

다음 코드는 파일 전체를 한 번에 메모리에 적재한다.

```java
byte[] bytes = Files.readAllBytes(Path.of("path"));
out.write(bytes);
```

파일이 크면 파일 크기만큼 메모리를 사용하게 된다.

### 6.2 스트림을 사용하는 코드

스트림을 사용하면 정해진 크기의 버퍼만 메모리에 올려 파일을 처리할 수 있다.

```java
try (InputStream is = Files.newInputStream(Path.of("path"))) {
    byte[] buffer = new byte[8192]; // 8KB
    int read;

    while ((read = is.read(buffer)) != -1) {
        out.write(buffer, 0, read);
    }
}
```

Java에서는 다음과 같이 더 간단하게 작성할 수도 있다.

```java
try (InputStream is = Files.newInputStream(Path.of("path"))) {
    is.transferTo(out);
}
```

> 대용량 데이터를 처리할 때는 전체 데이터를 메모리에 적재하기보다 스트림을 활용한다.

## 7. 응답 데이터 압축

응답 시간에는 서버 처리 시간뿐 아니라 데이터 전송 시간도 포함된다.

전송 시간은 다음 요소의 영향을 받는다.

- 네트워크 속도
- 네트워크 지연 시간
- 응답 데이터 크기

응답 데이터를 압축하면 전송되는 데이터의 크기를 줄일 수 있다.

대표적인 압축 방식:

- gzip
- Brotli

압축은 다음 데이터에 효과적이다.

- HTML
- CSS
- JavaScript
- JSON
- XML
- 일반 텍스트

이미 압축된 이미지나 영상 파일은 추가로 압축해도 효과가 작을 수 있다.  
압축과 해제에는 CPU 비용이 발생하므로 데이터 크기와 형식에 따라 적용해야 한다.

## 8. 정적 자원과 브라우저 캐시

JavaScript, CSS, 이미지와 같이 자주 변경되지 않는 정적 자원은 매번 서버에서 내려받지 않도록 브라우저 캐시를 활용한다.

브라우저 캐시를 적용하면 다음 효과를 얻을 수 있다.

- 정적 자원 요청 감소
- 페이지 로딩 시간 단축
- 서버 트래픽 감소
- 네트워크 사용량 감소

정적 자원의 내용이 변경되었을 때 이전 캐시가 사용되는 문제는 파일명에 버전이나 해시를 포함해 해결할 수 있다.

```text
app.css
app.a1b2c3.css
```

파일 내용이 변경되면 해시도 변경되므로 브라우저가 새로운 파일을 내려받는다.

---

## 9. 정적 자원과 CDN

브라우저 캐시를 사용해도 처음 접속하는 사용자가 많으면 원본 서버로 정적 자원 요청이 집중될 수 있다.

이때 **CDN(Content Delivery Network)**을 사용할 수 있다.

<img width="433" height="180" alt="CDN 구조" src="https://github.com/user-attachments/assets/357d590a-7512-4052-90d5-17f741380880" />

CDN은 정적 자원을 여러 지역의 서버에 캐싱한다.  
사용자는 원본 서버가 아니라 지리적으로 가까운 CDN 서버에서 정적 자원을 내려받는다.

CDN을 사용하면 다음 효과를 얻을 수 있다.

- 원본 서버의 트래픽 감소
- 정적 자원 응답 시간 단축
- 지역에 따른 네트워크 지연 감소
- 순간적인 트래픽 증가에 대한 대응력 향상

---

## 10. 대기 처리

사용자가 순간적으로 폭증할 때마다 서버 자원을 확장하는 것은 비효율적일 수 있다.  
트래픽 증가가 짧은 시간 동안만 발생한다면 확장한 자원이 곧 불필요해질 수 있기 때문이다.

이런 경우 시스템이 처리할 수 있는 요청만 받아들이고, 나머지 사용자를 대기시키는 방법을 사용할 수 있다.

대기 처리는 다음 상황에 적합하다.

- 이벤트 티켓 예매
- 선착순 상품 판매
- 수강 신청
- 한정 상품 구매
- 순간적으로 사용자가 집중되는 서비스

대기 처리를 사용하면 다음 효과를 얻을 수 있다.

- 서버가 처리할 수 있는 수준으로 요청량을 제한한다.
- 높은 부하로 전체 서비스가 중단되는 상황을 방지한다.
- 사용자가 계속 실패하는 대신 자신의 순서를 기다리게 할 수 있다.

단, 대기 시스템 자체에도 다음 기능이 필요하다.

- 대기 순서 관리
- 예상 대기 시간 안내
- 중복 입장 방지
- 이탈 사용자 처리
- 우회 요청 방지
- 대기 시스템 장애 대응

> 순간적인 트래픽 폭증 상황에서는 전체 서비스가 중단되는 것보다 사용자가 자신의 차례를 기다리게 하는 편이 나을 수 있다.

## 정리

서비스가 느려졌을 때는 먼저 처리량과 응답 시간을 측정해야 한다.  
그다음 실제 병목 지점을 찾아 적절한 개선 방법을 적용해야 한다.

주요 개선 방법은 다음과 같다.

- 목표 TPS와 응답 시간을 설정한다.
- 수직 확장 또는 수평 확장으로 처리량을 높인다.
- DB 커넥션 풀의 크기와 대기 시간을 조정한다.
- 캐시를 사용해 DB 조회와 반복 계산을 줄인다.
- 불필요한 객체 생성과 대량 메모리 할당을 줄인다.
- 응답 데이터를 압축해 전송 시간을 줄인다.
- 브라우저 캐시와 CDN으로 정적 자원 요청을 분산한다.
- 순간적인 트래픽 폭증에는 대기 처리를 적용한다.

> **핵심 원칙:** 성능 문제는 감으로 해결하지 않는다. 목표를 설정하고, 측정하고, 병목을 찾은 뒤 개선 결과를 다시 검증한다.
