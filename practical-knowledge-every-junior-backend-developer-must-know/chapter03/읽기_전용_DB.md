# 🌱 읽기 전용 DB (Primary-Replica)

> 3.3 DB 장비 확장하기 에서 뻗음
> 상태: 씨앗

## 왜 궁금해졌나

조회를 복제 DB로 보내면 처리량이 는다는 건 알겠는데,
**복제되기 전에 조회하면 옛날 데이터가 나오는 거 아닌가?**

## 파고들 질문

### 구조

- [ ] 변경 데이터는 어떤 방식으로 전파되나 (binlog?)
- [ ] 동기 복제 vs 비동기 복제, 뭘 쓰나
- [ ] 애플리케이션은 어떻게 Primary/Replica를 갈라 보내나
      (DataSource 분리? @Transactional(readOnly=true)?)

### 단점 / 함정

- [ ] **복제 지연(replication lag)** — 방금 쓴 걸 바로 못 읽는 문제
      → 글을 쓰고 목록으로 돌아갔는데 내 글이 없다면?
- [ ] 지연이 얼마나 나면 문제인가? 어떻게 모니터링하나
- [ ] Primary가 죽으면 어떻게 되나 (failover)
- [ ] Replica를 늘리면 무한정 좋아지나? 한계는?

### 판단

- [ ] 언제 도입을 결정하나 — 조회 비중이 몇 %일 때?
- [ ] 캐시 서버와 비교하면 어느 쪽이 먼저인가?
- [ ] 고정 비용이 는다는데, 손익 분기는 어떻게 계산하나

## 도입 경험이 있다면 물어볼 것

- [ ] 도입 **의도**가 무엇이었나 (성능? 가용성? 백업?)
- [ ] 복제 지연 때문에 사고가 난 적이 있나
- [ ] 어떤 쿼리를 Primary로 남겨뒀나, 그 기준은?
