## 1. 서버와 동시 실행

서버는 여러 사용자의 요청을 동시에 처리한다.

예를 들어 요청 하나를 처리하는 데 0.1초가 걸리고 초당 100개의 요청을 처리해야 한다면, 서버는 여러 요청을 병렬로 처리해야 한다. 요청을 하나씩 순차 처리하면 처리량은 낮아지고 응답 시간은 길어진다.

서버의 대표적인 동시 요청 처리 방식은 다음과 같다.

- 요청마다 스레드를 할당하는 방식
- 비동기 I/O 또는 논블로킹 I/O 방식

비동기 I/O를 사용하더라도 실제 서버는 여러 스레드를 사용하는 경우가 많다. 즉, 서버 개발에서는 여러 실행 흐름이 같은 데이터에 접근할 수 있다는 전제가 필요하다.

### 경쟁 상태

**경쟁 상태(Race Condition)**는 여러 스레드가 공유 자원에 동시에 접근할 때, 실행 순서에 따라 결과가 달라지는 문제다.

다음 코드는 안전하지 않다.

```java
private int count = 0;

public void inc() {
    count = count + 1;
}
```

`count = count + 1`은 실제로 다음 순서로 실행된다.

1. `count` 값을 읽는다.
2. 읽은 값에 1을 더한다.
3. 결과를 다시 저장한다.

두 스레드가 같은 값을 읽은 뒤 각각 저장하면 증가 요청 일부가 유실된다.  
따라서 10,000번 증가시켜도 결과가 10,000보다 작게 나올 수 있다.

> **핵심:** 여러 요청이 공유 가변 데이터를 수정한다면 동시성 문제가 발생할 수 있다.

## 2. 잘못된 데이터 공유

동시성 문제는 단순 카운터뿐 아니라 요청 데이터를 객체 필드에 저장할 때도 발생한다.

다음과 같은 Spring 싱글톤 빈은 위험하다.

```java
public class PayService {
    private Long payId;

    public PayResp pay(PayRequest req) {
        this.payId = genPayId();
        saveTemp(this.payId, req);

        PayResp resp = sendPayData(this.payId);
        applyResponse(resp);
        return resp;
    }
}
```

스레드 1이 `payId = 1`을 저장한 뒤, 스레드 2가 `payId = 2`로 변경할 수 있다. 이후 스레드 1은 자신이 생성한 결제 1이 아니라 결제 2의 데이터를 수정하게 된다.

이 문제는 다음 결과를 만든다.

- 고객 A의 결제 결과가 사라짐
- 고객 B의 결제 데이터에 고객 A의 결과가 저장됨
- 잘못된 사용자 데이터 노출 또는 결제 처리 오류 발생

해결 방법은 요청별 데이터를 필드에 저장하지 않는 것이다.

```java
public PayResp pay(PayRequest req) {
    Long payId = genPayId();

    saveTemp(payId, req);
    PayResp resp = sendPayData(payId);
    applyResponse(payId, resp);

    return resp;
}
```

> Spring 싱글톤 빈은 상태 없는 객체로 유지한다. 요청별 데이터는 지역 변수와 파라미터로 전달한다.

DB에서도 같은 문제가 발생한다. 예를 들어 관리자가 주문을 배송 상태로 바꾸는 동안 고객이 주문을 취소하면, 최종 상태가 실행 순서에 따라 취소 또는 배송으로 달라질 수 있다.

## 3. 잠금을 이용한 동시 접근 제어

잠금(Lock)은 공유 자원에 한 번에 하나의 스레드만 접근하게 하는 방식이다.

일반적인 흐름은 다음과 같다.

1. 잠금을 획득한다.
2. 공유 자원에 접근한다. 이 영역을 **임계 영역(Critical Section)**이라고 한다.
3. 잠금을 해제한다.

### ReentrantLock

`HashMap`은 여러 스레드가 동시에 수정하면 안전하지 않다. 잠금으로 접근을 직렬화할 수 있다.

```java
private final Lock lock = new ReentrantLock();
private final Map<String, UserSession> sessions = new HashMap<>();

public void addUserSession(UserSession session) {
    lock.lock();
    try {
        sessions.put(session.getSessionId(), session);
    } finally {
        lock.unlock();
    }
}
```

`synchronized`도 같은 목적에 사용할 수 있다.

- `synchronized`: 문법이 간단하고 블록 종료 시 자동 해제
- `ReentrantLock`: 잠금 획득 대기 시간 지정 등 추가 기능 제공

한 코드 영역에서 두 방식을 섞기보다 하나로 통일한다.

### 세마포어

**세마포어(Semaphore)**는 동시에 실행할 수 있는 작업 수를 제한한다.

예를 들어 외부 API 호출을 최대 5개로 제한할 수 있다.

```java
private final Semaphore semaphore = new Semaphore(5);
```

세마포어는 공유 데이터를 보호하기보다 외부 시스템, 파일 처리, 무거운 작업 등의 **동시 실행량 제한**에 적합하다.

### 읽기·쓰기 잠금

조회가 많고 수정이 적은 데이터에는 `ReadWriteLock`이 적합하다.

- 읽기 잠금: 여러 스레드가 동시에 획득 가능
- 쓰기 잠금: 한 스레드만 획득 가능
- 쓰기 중에는 읽기 불가
- 읽기 중에는 쓰기 불가

단순 잠금은 조회도 하나씩 처리하지만, 읽기·쓰기 잠금은 조회를 병렬 처리해 읽기 성능을 높일 수 있다.

## 4. 원자적 타입과 동시성 지원 컬렉션

### 원자적 타입

단순 카운터, 플래그, 숫자 변경에는 잠금보다 원자적 타입이 적합할 수 있다.

```java
private final AtomicInteger count = new AtomicInteger(0);

public void inc() {
    count.incrementAndGet();
}
```

`AtomicInteger`, `AtomicLong`, `AtomicBoolean` 등은 CAS(Compare And Swap) 연산을 사용해 값을 원자적으로 변경한다.

장점:

- 단순한 값 변경 코드가 간결함
- 잠금 대기로 인한 비용을 줄일 수 있음

제약:

- 여러 필드의 상태를 함께 검증하고 변경하는 복합 로직에는 단독으로 부족할 수 있음

### 동시성 지원 컬렉션

`HashMap`, `HashSet` 같은 일반 컬렉션은 여러 스레드가 동시에 수정하면 데이터가 깨질 수 있다.

대안은 다음과 같다.

- `Collections.synchronizedMap()`: 모든 접근을 동기화
- `ConcurrentHashMap`: 잠금 범위를 줄여 동시 접근 성능 개선
- 불변 객체: 변경하지 않고 새 값을 생성해 공유

동시 수정이 필요한 맵에는 일반적으로 `ConcurrentHashMap`을 우선 검토한다.

> **핵심:** 공유 가변 상태가 적을수록 잠금도 적게 필요하다.

## 5. DB와 동시성

DB 트랜잭션은 여러 쿼리를 하나의 작업으로 묶는다.

- 모든 변경 성공 시 커밋
- 중간 실패 시 전체 롤백

하지만 트랜잭션만으로 동시에 같은 데이터를 수정하는 문제까지 자동으로 해결되지는 않는다. 이때 비관적 잠금 또는 낙관적 잠금을 사용한다.

### 비관적 잠금

**비관적 잠금(Pessimistic Lock)**은 먼저 데이터를 읽은 트랜잭션이 잠금을 획득하고, 다른 트랜잭션은 대기하는 방식이다.

```sql
SELECT *
FROM orders
WHERE id = ?
FOR UPDATE;
```

특징:

- 같은 레코드에 대한 동시 수정을 막음
- 먼저 처리한 트랜잭션 결과를 다음 트랜잭션이 확인 가능
- 잠금을 기다리는 시간이 발생함

주문 배송과 취소가 동시에 발생한 경우, 먼저 잠금을 획득한 작업만 상태를 변경한다. 뒤늦게 잠금을 획득한 작업은 변경된 상태를 확인하고 실패 처리한다.

다음 상황에 적합하다.

- 동일 데이터 충돌이 자주 발생함
- 상태 전이가 엄격함
- 트랜잭션 안에 외부 결제 취소 같은 되돌리기 어려운 작업이 있음

### 낙관적 잠금

**낙관적 잠금(Optimistic Lock)**은 데이터를 읽을 때 버전 값을 함께 조회하고, 수정 시점에 같은 버전인지 비교한다.

```sql
UPDATE orders
SET state = 'SHIPPING',
    version = version + 1
WHERE id = ?
  AND version = ?;
```

수정된 행 수가 0이면 다른 트랜잭션이 먼저 수정한 것이다. 현재 작업은 실패 처리하고 롤백하거나 재시도한다.

특징:

- 잠금 대기 시간이 없음
- 충돌 시 빠르게 실패 응답 가능
- 충돌 빈도가 높으면 재시도와 실패가 많아짐

외부 결제 취소를 먼저 실행하고 이후 낙관적 잠금 충돌로 DB 수정에 실패하면, 외부 결제만 취소되고 DB는 롤백될 수 있다. 이 경우 비관적 잠금 또는 **트랜잭션 아웃박스 패턴**을 사용한다.

### 증분 쿼리

카운터를 증가시킬 때 조회 후 애플리케이션에서 `+1` 계산을 하면 증가분이 유실될 수 있다.

```sql
UPDATE subject
SET join_count = join_count + 1
WHERE id = ?;
```

증분 쿼리는 DB가 원자적으로 처리할 수 있다. 단, 사용하는 DB에서 해당 연산의 원자성이 보장되는지 확인해야 한다.

## 6. 잠금 사용 시 주의 사항

### 잠금 해제

잠금과 세마포어 퍼밋은 반드시 반환해야 한다.

```java
lock.lock();
try {
    // 임계 영역
} finally {
    lock.unlock();
}
```

`finally`에서 해제하지 않으면 예외 발생 시 잠금이 남아 다른 요청이 무한히 대기할 수 있다.

### 대기 시간 제한

잠금 획득을 무한히 기다리면 응답 시간이 길어지고 서버 자원이 고갈될 수 있다.

```java
boolean acquired = lock.tryLock(5, TimeUnit.SECONDS);
```

일정 시간 안에 잠금을 얻지 못하면 빠르게 실패 처리한다. 서비스 목표 응답 시간에 맞는 제한 시간이 필요하다.

### 교착 상태

**교착 상태(Deadlock)**는 두 작업이 서로가 가진 잠금을 기다리며 영원히 진행하지 못하는 상태다.

예시:

1. 스레드 1이 자원 A 잠금 획득
2. 스레드 2가 자원 B 잠금 획득
3. 스레드 1이 자원 B 잠금 대기
4. 스레드 2가 자원 A 잠금 대기

예방 방법:

- 잠금 획득 대기 시간 제한
- 여러 자원을 잠글 때 항상 동일한 순서 사용  
  예: ID가 작은 자원 → 큰 자원 순서

### 라이브락과 기아 상태

- **라이브락**: 작업은 계속 시도하지만 서로 양보만 반복해 실제 진행이 없는 상태
- **기아 상태**: 우선순위가 낮거나 자원을 얻지 못한 작업이 계속 실행되지 못하는 상태

라이브락은 우선순위, 임의 대기 시간, 중재 방식으로 줄인다. 기아 상태는 독점 시간과 우선순위를 관리해 완화한다.

## 7. 단일 스레드 처리

공유 상태를 한 스레드만 수정하게 하면 잠금 자체를 줄일 수 있다.

구조는 다음과 같다.

```text
요청 스레드 → 작업 큐 → 상태 관리 스레드 → 상태 변경
```

요청을 처리하는 여러 스레드는 상태를 직접 수정하지 않는다. 필요한 작업만 큐에 넣고, 상태 관리 스레드 하나가 순서대로 처리한다.

장점:

- 경쟁 상태 방지
- 교착 상태 방지
- 상태 변경 코드 단순화

제약:

- 큐와 비동기 응답 처리 구조가 필요함
- 상태 관리 스레드가 병목이 될 수 있음
- 임계 영역이 짧고 동시 요청이 적으면 일반 잠금 방식이 더 단순하고 빠를 수 있음

> 공유 메모리보다 큐·채널·불변 복제본을 통한 데이터 전달은 동시성 문제를 줄인다.

## 정리

동시성 문제는 여러 요청이 같은 가변 데이터를 동시에 수정할 때 발생한다.

주요 대응 방법은 다음과 같다.

- 싱글톤 빈에 요청별 상태를 저장하지 않는다.
- 단순 값 변경에는 원자적 타입을 사용한다.
- 공유 자원 보호에는 잠금, 읽기·쓰기 잠금, 동시성 컬렉션을 사용한다.
- 외부 호출 동시 수 제한에는 세마포어를 사용한다.
- DB 충돌에는 비관적 잠금 또는 낙관적 잠금을 적용한다.
- 카운터는 증분 쿼리로 처리한다.
- 잠금은 `finally`에서 해제하고, 대기 시간과 획득 순서를 관리한다.
- 복잡한 공유 상태는 단일 스레드와 작업 큐 방식도 검토한다.

> **핵심 원칙:** 공유 가변 상태를 최소화하고, 남은 공유 자원에는 충돌 빈도와 작업 특성에 맞는 동시성 제어 방식을 적용한다.
